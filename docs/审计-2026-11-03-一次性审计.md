# 一次性审计：把「每审一次冒新问题」这个现象本身修掉

日期：2026-11-03
触发原话：**「怎么这么多问题，每让你审计一次你就会发现新的问题，你为什么不能一次性审计并处理好呢」**

这份报告不是「又一轮 diff 阅读」，而是**对审计方法本身做一次审计**：先解释为什么
每轮都能翻出新问题，再针对每个根因换成机械手段，然后一次性把机械手段报出来的
问题全部修掉，最后给出**仍然没用机械手段覆盖的清单**（不再假装「没问题了」）。

---

## 一、为什么每审一次都有新问题（根因，不是借口）

| # | 根因 | 后果 |
|---|---|---|
| 1 | **增量审查陷阱**：上一轮只审「上一个提交的 diff」 | 每修一次就产生新代码面，下一轮在新面上再抽样，永远审不完 |
| 2 | **人工抽样 vs 代码体量**：19,700 行 Zig、360 个分配点、2,900 个 `try`、20 种查询形态 | 抽样必然只捞到一两处；捞到哪处取决于读代码时的注意力，不取决于缺陷分布 |
| 3 | **没有机械护栏**：同一类缺陷（所有权/分配器/语义分歧）没有任何「跑测试就报」的检查 | 已修的问题不会回归，未修的问题不会自己暴露 |

结论：问题不是「我这次不够仔细」，而是**方法本身不收敛**。要收敛，必须把每一类
缺陷都变成「机器每次都查一遍」的东西。

## 二、缺陷分类 → 机械手段（这是本次真正的交付物）

| 缺陷类别 | 机械手段 | 本次之前的覆盖 | 本次之后 |
|---|---|---|---|
| 泄漏 / 重复释放 / 分配器错配（查询装配） | `checkAllAllocationFailures` | 18 条语句 | 18 条语句（沿用） |
| 泄漏 / 重复释放（**开库 / 恢复 / 重开**） | 自驱 OOM 扫描（199 个注入点） | **0** | 全生命周期 |
| 语义：索引 vs 全扫、排序、LIMIT/OFFSET、NULL、投影 | **差分随机测试**（单表 500 条） | **0** | 全覆盖 |
| 语义：JOIN 三条执行路径（哈希 / 索引嵌套 / 全表扫兜底） | **差分随机测试**（JOIN 260 条） | **0** | 全覆盖 |
| 语义：UPDATE / DELETE + 索引维护 | **差分对账**（30 轮 × 6 条 DML） | **0** | 全覆盖 |
| 编译期功能矩阵（`sql`/`mmap`/`threads`/`alloc` 可关） | — | 0 | **仍未做**（见第五节） |

差分测试的三条口径（写死，避免比出噪声）：
1. **`ORDER BY` 末位自动补主键**——否则相同键的先后在 SQL 里未定义，各条执行路径
   各给一个次序都「合法」，比出来的差异是噪声。
2. **无 `ORDER BY` 时按多重集比对**（排序后逐格比）——无 ORDER BY 的行序未定义，
   但**结果集必须相同**，这正是「建索引不改变结果」那条不变量。
3. **`LIMIT`/`OFFSET` 只在有 `ORDER BY` 时生成**——否则「取前 N 行」本就未定义。

## 三、机械手段一次扫出的问题（全部已修）

### P1 · 投影列顺序完全不生效（正确性，最严重）

```sql
SELECT s, id, g FROM t        -- 列名: s, id, g
                              -- 值:   1, NULL, NULL   ← 实际是 (id, g, s)
```

根因：`buildOutput` 用 **`m.ncols == proj.indices.len`** 推断「`flat` 已经是最终布局，
可以转移所有权」。而「全列解码」（`ncols == 表列数`）与「全列但乱序的投影」
（`indices.len == 表列数`）两个条件同时成立时，长度相等而布局是**表顺序**。

为什么以前没发现：**所有既有用例的投影都是表序**（`SELECT id, g`、`SELECT id, s`、
`SELECT id, n`…… 全仓 grep 确认），乱序投影一次都没测过。

修法：给 `Materialized` 加显式标记 `pushed: bool`，只有「按投影解码」这条路径才置真；
不再用长度去推断布局。`JoinSink.materialize` 写的就是投影顺序，置 `true`。

**撤销验证**：把 `if (m.pushed)` 改回 `if (m.ncols == proj.indices.len)`，
`zig build test` 立刻红（`[MISMATCH #22] SELECT g, s, id FROM t ORDER BY g, id`）。

### P2 · `Engine.open` 失败路径漏释放 map 键

`Engine.deinit` 释放了 `tables` / `idx_tables` 的 key（都是自己 `dupe` 的），
但 `open` 里的两条 `errdefer` **只释放 value**。开库中途失败（磁盘满、段损坏）
会漏掉每个表名与索引名的 dupe。触发证据：生命周期守卫报 `len: 7`（= `idx_a_g`）。

修法：两条 `errdefer` 补齐 `alloc.free(key_ptr.*)`，与 `deinit` 同口径。

**撤销验证**：去掉那行 `alloc.free(x.key_ptr.*)` ⇒ `[life] fail_index=161 记账不平：
alloc=49581 free=49574`（正好差 7 字节）。

### P3 · `decodeRowProjected` 静默产出未初始化内存

文档写着「`want` **必须严格升序**」，但函数没有任何校验。喂非升序时游标 `wi`
单向前进，后面那些目标单元**根本不会被写**，`flat` 直接把 `undefined` 当结果返回——
不报错、不崩溃，只在特定内存内容下表现为错误数据。

修法：循环结束后一次判定 `if (wi != want.len) return error.InvalidProjection;`。
非升序 / 越界 / 重复值都必然导致「有 wanted 列从未被匹配 ⇒ `wi` 走不满」，
所以这一个比较就能全部覆盖，**不给热路径加逐行扫描**（第一版写成前置 O(n) 校验，
等于每行多一次循环，已改）。

### P4 · 差分脚手架自身的 use-after-free（不是引擎缺陷，但值得记）

`fetchAll` 第一版只浅拷 `sql.Value`，text 切片指向 `Rows.buf`，而 `Rows.deinit`
会把 `buf` 整块释放 ⇒ 读到 `0x55` 填充，一度误判成「引擎把文本存坏了」。

诊断靠的是**把字节打成十六进制**（`'U'` 的 `0x55` 与长度正确立即指向「内容悬垂」），
不是靠猜。教训：**差分测试的脚手架自己必须深拷**，否则会把脚手架 bug 记到引擎账上。

## 五、仍然没有机械覆盖的清单（如实列出，不再说「没问题了」）

1. **聚合 / GROUP BY / HAVING 没有差分**（`COUNT/SUM/AVG/MIN/MAX` 与分组、`HAVING`）。
2. **`UPDATE` 改主键**没覆盖（生成器显式跳过：改主键会让参考表主键集合分叉，
   需要单独的用例）。
3. **WAL 重放中途截断 / 段损坏的恢复路径**只有「正常重开」被 OOM 注入覆盖，
   损坏注入（截断文件、篡改 CRC）还没有。
4. **编译期功能矩阵没有落地**：项目指令 §16.5 要求 `sql`/`mmap`/`threads`/`alloc`
   都能编译期关掉，但当前代码里**没有这些开关**，所以「关掉也能编译并跑 KV 回归」
   这条约束**无法验证**。这是一条真缺口，不是「已通过」。
5. `ORDER BY <索引列>` 仍约 0.97×（性能向，非正确性），复合索引未做。

## 六、方法论沉淀

1. **每类缺陷必须有一个「机器每次都查」的手段**，人眼只用来处理机器报出来的差异。
2. **差异比「想」可靠**：差分随机测试 + 独立朴素参考实现，能在几分钟内覆盖人工
   审一周也读不完的组合空间。
3. **差分口径必须先消除「未定义」**（排序并列、无 ORDER BY 的行序、无 ORDER BY 的
   LIMIT），否则报出来的都是噪声，比不测更糟（会麻木）。
4. **每修一处必须做撤销验证**：撤掉修复 ⇒ 守卫必须红。否则不知道守卫有没有用。
5. **守卫的覆盖面也要审**：上一轮的守卫只盖「读」，这一轮补「写 + DDL + 重开」，
   才把 `Engine.open` 的键泄漏翻出来。
