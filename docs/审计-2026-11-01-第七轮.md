## P1-1　`+28%` 不可成立，实测配对收益是 `+16%`

### 问题

原报告的数字链是：

1. **本批**（`concat-run`）测出「25 段 ÷ 1 段」= `26,725,820 / 30,569,074` = **0.874**；
2. 拿它去比**上一批**（`mergegap`）的同一个比值 = `20,814,687 / 28,033,663` = **0.742**；
3. 得出「归并代价 1.35× → 1.14×，即 +28%」。

第 2 步与第 1 步跨批次。而本批 CSV 里已经有反证：

| 轮次 | `cm_count_before`（25 段） | `cm_count_after`（1 段） | 比值 |
|---|---|---|---|
| run1 | 22,431,081 | 22,228,743 | **1.009**（25 段反而更快！） |
| run2 | 26,725,820 | 31,322,041 | 0.853 |
| run3 | 26,970,753 | 30,569,074 | 0.882 |

**同一个二进制、同一张表、同一份数据**，比值从 1.009 跨到 0.853，15 个百分点。
在这个噪声水平上，「跨批次差 14%」什么也证明不了。

### 修复

给 `Table.Options` 加 `no_concat`（**仅基准用，生产恒 false**），把「要不要拼接」变成同一进程内的开关：

```zig
cam_opts.no_concat = true;   // 强制走 k 路堆归并
cam_opts.no_concat = false;  // 走顺序拼接
```

基准档 `cm_ab_{on,off}`：同一张 25 段表、背靠背交替跑，**奇偶轮交换先后顺序**，
抵消「先跑的那一边更冷/更热」的系统偏差；每轮同时打印比较次数作为「确实跑在目标路径上」的凭据。

### 实测（3 轮 × 3 对 = 9 对，行/秒）

| 轮 | 对 | off（堆归并） | on（顺序拼接） | 比值 |
|---|---|---|---|---|
| run1 | 1 | 34,439,768 | 42,541,968 | 1.235 |
| run1 | 2 | 29,568,128 | 37,499,531 | 1.268 |
| run1 | 3 | 35,364,681 | 36,101,865 | 1.021 |
| run2 | 1 | 39,383,103 | 45,634,595 | 1.159 |
| run2 | 2 | 40,350,891 | 46,892,878 | 1.162 |
| run2 | 3 | 40,485,502 | 48,300,779 | 1.193 |
| run3 | 1 | 31,883,892 | 34,772,207 | 1.091 |
| run3 | 2 | 31,653,182 | 36,729,597 | 1.160 |
| run3 | 3 | 33,940,645 | 35,629,031 | 1.050 |

排序后：`1.021 | 1.050 | 1.091 | 1.159 | **1.160** | 1.162 | 1.193 | 1.235 | 1.268`

- **9/9 配对全部为正**（符号检验 p ≈ 2⁻⁹ ≈ 0.002）；
- **中位 +16.0%**，最小 +2.1%，最大 +26.8%。

### 确定性凭据（不依赖计时）

| 指标 | off | on |
|---|---|---|
| `cm_ab_*_compares`（50 万行） | **1,000,054** | **0** |
| `cm_cursors_before` | 25 | 25 |

`off` 侧的比较次数 `1,000,054` 与改造前实测**一字不差** —— 说明开关确实把行为切回了旧路径，
`on` 侧的 `0` 才是拼接生效。这比任何计时都可靠。

**修正后的结论：顺序拼接收益中位 +16%，不是 +28%。**

## P2-1　用例里的悬垂栈引用（UB）

`segment.zig` 的 Bloom 测试：

```zig
while (i < n) : (i += 1) {
    var k: [8]u8 = undefined;          // ← 声明在循环体内
    ...
    try w.push(&k, @intCast(i + 1), 0, "v");
}
_ = try w.finish(dir, tmp ++ "/000001.idx");   // ← 此时才读 last_key
```

`Writer` 现在记的是 key 的**地址**，到 `finish` 才读。循环体结束意味着 `k` 已过期。
实践中能跑通（同一栈帧、槽位未被覆盖），但属未定义行为 ——
而这恰恰是 `last_key` 引用语义最容易踩的坑，**测试自己先踩一遍不合适**。

已把 `k` 提到循环外，并注明原因。

## P2-2　新增不变量没有守门

`Writer.push` 这一轮多了一条隐式前提：**key 必须按升序调用**。
段头写的是「最后一个 `push` 的 key」，只有升序时它才等于段内最大 key。
一旦违序：

```
违序 push → 段头 max_key 偏小 → canConcat 把「其实重叠」判成不重叠
        → 顺序拼接按段依次产出 → 结果乱序 / 漏行
```

已在 `push` 加检查：

```zig
std.debug.assert(self.rows == 0 or keyCmpLessEq(self.last_key, key));
```

`std.debug.assert` 在 Debug/ReleaseSafe 有效，**ReleaseFast 整条抹除**（热路径零成本）。
58 个用例全部跑在 Debug 下且全绿 → 现有调用方（memtable 刷盘、compaction 归并、各测试）都满足。

## 已核对、确认无问题的项

| 检查项 | 结论 |
|---|---|
| `max_key_off` 基址一致性 | `open` / `fromBytes` 都用传给 `parseIdxHeader` 的同一个切片做基址，`self.idx` 构造后从未被替换 ✓ |
| 空段处理 | 中间空段会让**更早那次** `bmin = firstKey() orelse return false` 直接否掉整条链，保守正确；`maxKey() orelse continue` 只在「末尾/开头空段」生效，不影响顺序 ✓ |
| 段裁剪后的游标子集 | 裁剪只发生在「段首 ≥ end」一侧，保留下来的是**前缀**，拼接顺序不变 ✓ |
| `last_key` 生命周期（生产路径） | `flushImpl`：`finishBytes` 在 `mem.reset()` **之前**；`compact`：`finishBytes` 在旧段 `close()` **之前** ✓ |
| `RefCursor` 是否持有自有缓冲 | 无。`key`/`value` 直接指向 `seg.data`，`it.deinit()` 不影响已产出的 key ✓ |
| 跨段去重 | `canConcat` 要求 `maxKey(i-1) < firstKey(i)`（严格小于），跨段不可能有同 key，去重不会误删 ✓ |
| `scan_rows_read` 语义 | 三条路径（单游标 / 拼接 / 堆）都按「取出一条记录（含墓碑与重复）」计数，口径一致 ✓ |
| 归档读写 | `archiveAppend` / `archiveRewrite` 只搬运 payload 字节，与段内格式无关，无需跟着改 ✓ |
| 旧 magic 残留 | 全仓 grep `PEKZIX02` / `PEKZAG03` = **0 处** ✓ |
| 归并路径唯一性 | 全部归并都走 `MergeIter`（`exec.zig` 3 处、`main.zig` 5 处、`table.zig` 6 处），无第二份实现 ✓ |
| 重叠守门 | `merge2_cursors = 2`、`merge2_compares = 399,999`，三轮一致，与改造前完全相同 ✓ |

## 遗留候选（本轮刻意不做）

1. **反向段裁剪**：段头现在有 `maxKey()`，可以剪掉「整段在查询起点之前」的段（`maxKey() < start`）。
   3 行改动，对范围扫描/点查直接有益。需要单独一轮量。
2. **残余归因仍是推断**：原报告说「剩下的 1.14× 是 25 个游标初始化（1–2ms）」，这是**推断不是实测**。
   要确认得先补「游标初始化耗时」分档。在补之前应按「未定位」表述。
3. `cm_count_before` / `cm_count_after` 这对指标在本机噪声下已失去分辨力（批内比值 0.85–1.01），
   后续判断归并开销**一律用 `cm_ab` 配对**，不要再拿这对做跨批次对比。
