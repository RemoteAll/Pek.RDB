## 一、发现并已修的问题

### P0-1　归档残片会导致**新写入的段永久不可见**（数据丢失）

- **现象**：`seg/index.bin` 采用「追加 record」布局。若「追加 record 写到一半崩溃」，
  文件尾部会留一段残片；`ArchiveIter.next()` 遇到截断 record 就停下 —— 之后所有新追加的段
  都排在这段残片**后面**，于是**永远读不到**。用户会看到「刚写的数据重启后消失」，且不报错。
- **复现**：新增用例「index.bin 尾部残片后新增段必须仍可见」。
  未修复时实测 `expected 3, found 2`（第 3 段丢失）。
- **修复**：`ArchiveIter.validEnd()` 记录最后一条**完整** record 的末尾；`Table.index_valid_len`
  记住它；`flush` 从该位置写（**覆盖**残片而不是接在后面）。
  另外 `archiveAppend` 写完后 `setLength` 截断到新末尾 —— 否则新 record 比残片短时，
  尾部残留字节可能被当成一条「看似合法」的 record（hash 会拒，但会让整个库打不开）。
- **状态**：已修 + 用例守住（第 41 个用例）。

### P0-2　bench 里的二次释放（上一轮已修，本轮补全排查）

- `benchMain` 里 `t` 与 `t6` 都是「`defer deinit()` + 手动 `deinit()`」。
- 上一轮只修了 `t6`，本轮修 `t` 并**全仓 grep** 该模式：确认只有这两处，无第三处。
- 真修后移除了上一轮的 `std.process.exit(0)` 绕过，`zig-out\bin\spike-bench.exe` 退出码 0。

### P1-1　`readWholeFile` 异常路径 double free

```zig
const buf = try alloc.alloc(...);
errdefer alloc.free(buf);
const n = try f.readPositionalAll(...);
if (n != buf.len) { alloc.free(buf); return error.UnexpectedEndOfFile; }  // ← 再 free 一次
```

- 只在文件被截断时触发（罕见），但异常路径正是审计重点。
- **修复**：删掉手动 free，交给 `errdefer`。**已修**。

### P1-2　`Table.flush` 的 append 失败路径 double free

`Segment.fromBytes(..., take_ownership = true, ...)` 已接管索引字节，随后 `segs.append` 失败时
`seg.close()` 会 free 它，而外层的 `errdefer free(fin.bytes)` 又 free 一次。
- **修复**：失败路径把 `owns_idx` 置 false 再 close，字节只由 `errdefer` 释放。**已修**。

### P1-3　`dataView` 失败后仍标记「已映射」（状态污染）

`self.mapped = true` 写在尝试 mmap **之前**。一旦 mmap 失败（文件被删/OOM），
该段此后永远返回空视图，`get` 里 `view[begin..end]` 直接越界。
- **修复**：只有全部成功才置 `mapped = true`，失败允许下一次重试。**已修**。

### P1-4　`dataView` 的 `stat` 失败会泄漏句柄

`self.file = f` 已赋值，随后 `stat` 失败返回错误；下次重试会覆盖 `self.file`，旧句柄永久泄漏。
- **修复**：先 `stat`（失败即 close 再返回），成功后才落字段。**已修**。

表格里 11 行数字来自 `2026-10-31` 批，而「数据来源」已写成 `2026-11-01` 批。

# 第二轮审计：compaction（2026-11-01）

> 范围：`Table.compact()`、`MergeIter` 重构、归档格式 `PEKZAG03`、`archiveRewrite/archiveAppend`。
> 方法同上：读异常路径 → 写用例复现 → 修 → 回归。

## 发现并已修

### P0-1　归档 magic **从来没被写进去**（加校验后才暴露）

`archiveAppend` 用 `at < 8` 判断「是否新建」，但空库的 `index_valid_len` 初值就是 **8** ——
于是**首条 record 直接写在没有 magic 的文件头**。因为读取侧也从不校验 magic，功能一直"正常"。

本轮加了 `archiveCheckMagic` 之后，4 个用例立刻挂 `BadArchiveMagic`。修复：按**文件实际长度**
（`stat < 8`）判断是否需要补写 magic。

**这条值得单独记**：**缺失的校验会掩盖写入缺陷**。之前"能跑"不代表格式对。

### P0-2　`compact()` 异常路径会让 Table 变成空表

原次序是「重写归档 → 清空 `segs` → 建新段」。若最后 `fromBytes` 失败（索引解析失败 / OOM）：
内存里 `segs` 已空、`idx_archive` 已释放，而磁盘归档已指向新段 —— 该 Table 后续读写全部错误。

修复为**正确次序**：

1. 写新 `.data`（含 sync）
2. **在内存里构造新段**（顺便验证索引可解析）—— 失败则原表毫发无伤
3. 重写归档（临时文件 + 原子 rename）—— 成功后磁盘才指向新段
4. 关闭旧段、删除旧 `.data`
5. 装上新段

### P1-1　`Table.open` 不校验归档 magic

旧格式（`PEKZAG02`）会被按新布局（record 头 12→16 字节）解析成乱数据。已加校验，报 `BadArchiveMagic`。
新增用例：「归档 magic 不匹配必须报错」。

### P1-2　`MergeIter.init` 异常路径泄漏

`init` 中途失败时 `cursors` 已部分分配，而调用方的 `defer it.deinit()` 是在 `try init` **之后**才注册的
—— 泄漏。已改为 `init` 内部 `errdefer self.deinit()`。

### P1-3　`compact` 的 `before` 取值位置错

`before` 在 `flush()` **之前**取，若 memtable 非空，flush 会多产出一段，`before` 少算 1。

### P1-4　`archiveRewrite` 用 `page_allocator`

与 Table 的 allocator 混用，已改为由调用方传入。

## 确认无问题

- `MergeIter` 与 `scanRefs` 重构后行为一致（3 个既有 scan 用例 + compact 用例都过）
- 空 end（无上界）语义：`RefCursor`/`MemCursor` 已一致处理，`compact` 全量归并依赖它
- `compact` 后 `next_seg` 由归档里的 `max_id` 推导，不依赖段数
- 墓碑在全量合并时丢弃，测试覆盖「删除的 key 合并后仍返回 null」

## 结论

- 本轮审计 **6 个问题**（2 个 P0），全部已修；单测 43 → **44**。
- 性能无退化：`flush` 4.80M 行/s、`recover` 1.14ms、`big_recover` 1.72ms；
  compaction 效果不变（`cm_get_after` 867,204 对 `cm_get_before` 572,107，+52%）。
- **可以继续往下推进**。
