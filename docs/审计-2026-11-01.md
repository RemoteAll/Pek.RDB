## 一、发现并已修的问题

### P0-1　归档残片会导致**新写入的段永久不可见**（数据丢失）

- **现象**：`seg/index.bin` 采用「追加 record」布局。若「追加 record 写到一半崩溃」，
  文件尾部会留一段残片；`ArchiveIter.next()` 遇到截断 record 就停下 —— 之后所有新追加的段
  都排在这段残片**后面**，于是**永远读不到**。用户会看到「刚写的数据重启后消失」，且不报错。
- **复现**：新增用例「index.bin 尾部残片后新增段必须仍可见」。
  未修复时实测 `expected 3, found 2`（第 3 段丢失）。
- **修复**：`ArchiveIter.validEnd()` 记录最后一条**完整** record 的末尾；`Table.index_valid_len`
  记住它；`flush` 从该位置写（**覆盖**残片而不是接在后面）。
  另外 `archiveAppend` 写完后 `setLength` 截断到新末尾 —— 否则新 record 比残片短时，
  尾部残留字节可能被当成一条「看似合法」的 record（hash 会拒，但会让整个库打不开）。
- **状态**：已修 + 用例守住（第 41 个用例）。

### P0-2　bench 里的二次释放（上一轮已修，本轮补全排查）

- `benchMain` 里 `t` 与 `t6` 都是「`defer deinit()` + 手动 `deinit()`」。
- 上一轮只修了 `t6`，本轮修 `t` 并**全仓 grep** 该模式：确认只有这两处，无第三处。
- 真修后移除了上一轮的 `std.process.exit(0)` 绕过，`zig-out\bin\spike-bench.exe` 退出码 0。

### P1-1　`readWholeFile` 异常路径 double free

```zig

errdefer alloc.free(buf);
const n = try f.readPositionalAll(...);
if (n != buf.len) { alloc.free(buf); return error.UnexpectedEndOfFile; }  // ← 再 free 一次
```

- 只在文件被截断时触发（罕见），但异常路径正是审计重点。
- **修复**：删掉手动 free，交给 `errdefer`。**已修**。

### P1-2　`Table.flush` 的 append 失败路径 double free

`Segment.fromBytes(..., take_ownership = true, ...)` 已接管索引字节，随后 `segs.append` 失败时
`seg.close()` 会 free 它，而外层的 `errdefer free(fin.bytes)` 又 free 一次。
- **修复**：失败路径把 `owns_idx` 置 false 再 close，字节只由 `errdefer` 释放。**已修**。

### P1-3　`dataView` 失败后仍标记「已映射」（状态污染）

`self.mapped = true` 写在尝试 mmap **之前**。一旦 mmap 失败（文件被删/OOM），
该段此后永远返回空视图，`get` 里 `view[begin..end]` 直接越界。
- **修复**：只有全部成功才置 `mapped = true`，失败允许下一次重试。**已修**。

### P1-4　`dataView` 的 `stat` 失败会泄漏句柄

`self.file = f` 已赋值，随后 `stat` 失败返回错误；下次重试会覆盖 `self.file`，旧句柄永久泄漏。
- **修复**：先 `stat`（失败即 close 再返回），成功后才落字段。**已修**。

# 第二轮审计：compaction（2026-11-01）

> 范围：`Table.compact()`、`MergeIter` 重构、归档格式 `PEKZAG03`、`archiveRewrite/archiveAppend`。
> 方法同上：读异常路径 → 写用例复现 → 修 → 回归。

## 发现并已修

### P0-1　归档 magic **从来没被写进去**（加校验后才暴露）

`archiveAppend` 用 `at < 8` 判断「是否新建」，但空库的 `index_valid_len` 初值就是 **8** ——
于是**首条 record 直接写在没有 magic 的文件头**。因为读取侧也从不校验 magic，功能一直"正常"。

本轮加了 `archiveCheckMagic` 之后，4 个用例立刻挂 `BadArchiveMagic`。修复：按**文件实际长度**
（`stat < 8`）判断是否需要补写 magic。

**这条值得单独记**：**缺失的校验会掩盖写入缺陷**。之前"能跑"不代表格式对。

### P0-2　`compact()` 异常路径会让 Table 变成空表

原次序是「重写归档 → 清空 `segs` → 建新段」。若最后 `fromBytes` 失败（索引解析失败 / OOM）：
内存里 `segs` 已空、`idx_archive` 已释放，而磁盘归档已指向新段 —— 该 Table 后续读写全部错误。

修复为**正确次序**：

1. 写新 `.data`（含 sync）
2. **在内存里构造新段**（顺便验证索引可解析）—— 失败则原表毫发无伤
3. 重写归档（临时文件 + 原子 rename）—— 成功后磁盘才指向新段
4. 关闭旧段、删除旧 `.data`
5. 装上新段

### P1-1　`Table.open` 不校验归档 magic

旧格式（`PEKZAG02`）会被按新布局（record 头 12→16 字节）解析成乱数据。已加校验，报 `BadArchiveMagic`。
新增用例：「归档 magic 不匹配必须报错」。

### P1-2　`MergeIter.init` 异常路径泄漏

`init` 中途失败时 `cursors` 已部分分配，而调用方的 `defer it.deinit()` 是在 `try init` **之后**才注册的
—— 泄漏。已改为 `init` 内部 `errdefer self.deinit()`。

### P1-3　`compact` 的 `before` 取值位置错

`before` 在 `flush()` **之前**取，若 memtable 非空，flush 会多产出一段，`before` 少算 1。

### P1-4　`archiveRewrite` 用 `page_allocator`

与 Table 的 allocator 混用，已改为由调用方传入。

## 确认无问题

- `MergeIter` 与 `scanRefs` 重构后行为一致（3 个既有 scan 用例 + compact 用例都过）
- 空 end（无上界）语义：`RefCursor`/`MemCursor` 已一致处理，`compact` 全量归并依赖它
- `compact` 后 `next_seg` 由归档里的 `max_id` 推导，不依赖段数
- 墓碑在全量合并时丢弃，测试覆盖「删除的 key 合并后仍返回 null」

## 结论

- 本轮审计 **6 个问题**（2 个 P0），全部已修；单测 43 → **44**。
- 性能无退化：`flush` 4.80M 行/s、`recover` 1.14ms、`big_recover` 1.72ms；
  compaction 效果不变（`cm_get_after` 867,204 对 `cm_get_before` 572,107，+52%）。
- **可以继续往下推进**。

# 第三轮审计：自动触发 compaction（2026-11-01）

> 对象：提交 `550cf5d`（`Options.compact_after_segs`、`maybeAutoCompact`、`flushImpl` 拆分、
> `going_compact`、字节计数器、`bench_ac.zig`）。
> 方式：逐条对照实测量（两轮 §16.1.6 / §16.1.7）反查实现与文档，并验证用例有效性。

## P1-1　`compact()` 提前返回时虚增 `auto_compact_count`

`maybeAutoCompact()` 在 `segs.len >= compact_after_segs` 时调 `compact()`，然后无条件
`auto_compact_count +|= 1`。但 `compact()` 开头有 `if (segs.items.len <= 1) return` ——
**段数 ≤1 时它什么都没做，计数却加了**。

`compact_after_segs = 1` 时首次 flush 必现：1 段 → 达阈值 → compact 立即返回 → 计数虚增。

**修**：`CompactResult` 加 `did: bool`，只在 `cr.did` 时累加。
**用例**：「阈值 1 不得虚增合并次数」。**已验证有效性**：撤掉 `if (cr.did)` 后该用例失败
（`49 passed; 1 failed`，失败点正是 `expectEqual(@as(u32,0), auto_compact_count)`）。

## P1-2　失败到上限后永久停用，且上层看不见

`auto_compact_fails` 达 `AUTO_COMPACT_MAX_FAILS`(5) 后 `maybeAutoCompact` 直接 return，
**不会自动恢复**；而 `auto_compact_error` 只是个字段，没人读。

后果：一次临时故障（磁盘满 / OOM）就能让「自动合并」**永久静默失效**，
库退化成「段数只增不减」，而调用方毫无感知 —— 正是用户指令里禁止的「静默失败」。

**修**：加 `pub fn autoCompactHealthy()` + `pub fn resetAutoCompact()`，并在
`Options` / `maybeAutoCompact` / 架构 §16.1.7 第六节三处写明「上层必须查」。
**用例**：「失败到上限后停手，resetAutoCompact 能恢复」（伪造 fails=上限 → 不合并 → 重置 → 恢复）。

## P1-3　`compact()` 最后一步 `segs.append` 仍是 P0-2 的残留失败点

次序已是「写新 .data → 建新段 → 重写归档 → 清旧段 → 装新段」，但最后一步是
`try self.segs.append(...)`。此刻：归档已指向新段、旧段已删、`segs` 已 `clearRetainingCapacity`，
**若 append 失败，Table 就是空表**。

实际不会失败（刚装过 ≥2 个元素、容量够），但这是**靠容量隐式保证**，代码没表达出来。

**修**：①改 `appendAssumeCapacity()` 显式声明不失败；②把清理旧段的循环从
`alloc.print` + `defer free` 改成固定缓冲 `bufPrint` + `catch continue`，
顺手消除「归档重写之后还可能分配失败」的路径。

## P2-1　`auto_compact_bytes` 名不副实

字段在 `compact()` 里累加，**手动调 compact 也计入**，名字却叫 auto。
**修**：改名 `compact_bytes_total`，注释写明含手动合并、失败的不计。

## P2-2　`flush_bytes_total` 在 WAL 同步之前累加

`try self.wal.sync()` 若失败，调用方会重试 flush，同一批数据被统计两次 → 写放大失真。
**修**：移到函数末尾（WAL 同步成功之后）。

## P2-3　`compact()` 里 `defer free` 的作用域是整个函数

清理旧段的循环里 `defer self.alloc.free(op)` 不会在每轮结束释放，而是累积到函数返回。
段多时白占内存。**修**：改用固定缓冲后该 defer 直接消失。

## P2-4　`Options.compact_after_segs` 的注释与实测矛盾

原注释：「段数 ≤8 时点查衰减可忽略，≥16 后不命中点查开始明显变慢」。
但两轮实测都说不是这样：

- §16.1.6 段数曲线：2 段 13.54M → 7 段 4.15M，**7 段已比 2 段慢 3.3×**；
- §16.1.7：25 段 1.66M → 10 段 3.58M，**10 段已快 2.16×**。

不命中点查近似与段数成反比，**没有「≤8 段可忽略」这回事**。这条注释会直接误导选阈值。
**修**：重写为实测结论 + 推荐值 + 「只控触发时机、不解决单次阻塞」的边界说明。

## P2-5　`flush()` 的语义变化没写进 API 注释

开了自动合并后，`flush()` 可能从微秒级变成数百毫秒（200 万行 0.4–0.8 s）。
`put()` 内部也会调 `flush()` → **写路径会有延迟尖刺**。原注释没提。
**修**：`flush()` doc 写明可能触发合并及量级；`Options` 注释写明抖动可预测。

## P2-6　§16.1.7 的单次合并耗时是「手动收窄」的数字

正文写「200 万行单次约 390–700 ms」。但：

- 由中位数推算 = (3043.63 − 1599.41) / 3 = **481 ms**；
- 完整波动区间 = **340–786 ms**（(2762.84−1743.34)/3 到 (3856.55−1498.83)/3）。

390–700 既不是中位数推算也不是完整区间，是取中间挑出来的 —— 与「禁止挑数字」的纪律不符。
**修**：改成分列「中位数推算 481 ms」与「完整区间 340–786 ms」，并注明前一版是收窄的。

## 审计过程中自己引入又修掉的一个（记下来防复发）

为清理失败时的孤儿 `.data`，我先加了 `errdefer self.dir.deleteFile(io, data_path)`。
**这是错的**：`archiveAppend` / `archiveRewrite` 之后归档已引用该文件，此时删掉它，
下次 `open` 会对不存在的文件报错 —— **把一个「留垃圾文件」的小问题换成了「库打不开」的大问题**。

**修**：加 `orphan_maybe` 标志，归档引用后置 false；errdefer 只在「归档尚未引用」时生效。

**沉淀**：**errdefer 的生效范围必须以「归档/清单是否已引用」为界**，
不能用「函数是否返回错误」为界。清理类 errdefer 都要问一句「此刻磁盘上的权威记录是否已经指向它」。

- `zig build check`（linux-musl）→ 0；`zig build mcu -Dtarget=riscv32-freestanding` → 0

- 确定性指标不变：1.000 / 1.645 / 2.815 / 5.670×，50 万与 200 万在阈值 8 都是 2.815×

本轮 **9 个问题**（3 P1 + 6 P2，其中 P1-3 是上一轮 P0-2 的残留失败点）+
**1 个审计中自引入并修掉的问题**，全部已修。可以继续往下推进。

# 第四轮审计：上一轮修复本身 + Writer 的资源泄漏（2026-11-01）

> 对象：提交 `014b707`（第三轮审计的修复）。
> 方式：逐条复核上轮修复的**失败语义**，并用 `checkAllAllocationFailures` 在**每个分配点**注入 OOM。
> 结果：4 个 P1 + 1 个 P2 已修，另记录 1 个无法自动化的测试缺口。单测 50 → 52。

## P1-1　上一轮我加的 `errdefer deleteFile(.data)` 是错的

第三轮我为「清理失败后的孤儿 .data」给 `flushImpl` 加了：

```zig
var orphan_maybe = true;
errdefer if (orphan_maybe) self.dir.deleteFile(self.io, data_path) catch {};
```

它安全的前提是「函数返回错误 ⇒ 归档未引用该文件」。但 `archiveAppend` 是
**写 record → `setLength` → `sync`** 三段：`sync` 失败时磁盘上**已经有完整 record**，
只是 `index_valid_len` 没更新。此时删掉 `.data`，归档里就留下一条指向不存在文件的 record，
**下次 `open` 报 FileNotFound** —— 把「留一个垃圾文件」换成了「库打不开」。

**修**：`flushImpl` 里**不删**。理由三条：

1. `next_seg` 没递增，下次 flush 会用**同一路径**覆盖，天然自愈；
2. 最坏情况只是多一个文件，代价远小于库打不开；
3. 万一是「写成功但没回传」，保留它反而能恢复到磁盘一致的状态。

`compact()` 里的同名清理**保留**，但补上为什么两边不一样：`archiveRewrite` 是
「写 tmp → sync → rename」，任何一步失败都意味着归档**原封未动**，此时删新 `.data` 是安全的。

## P1-2　`Writer` 的失败路径从头到尾都在泄漏（M1 起就存在）

`Writer.finishBytes` 只在**成功路径末尾**释放 `entries`（含每项 key）、`hashes`、`buf`、`scratch`，
并 `close` 文件。而：

- `push` 失败（OOM）→ 4 个缓冲 + 文件句柄全泄漏；
- `flushBuf` / `file.sync` 失败 → 同上，且**文件没 close**；
- 四处调用点（`flushImpl`、`compact`、两个测试）**都没有任何清理**。

`std.testing.allocator` 没报，因为测试走的都是成功路径 —— 这正是「只在成功路径验证」的盲区。

**修**：给 `Writer` 加**幂等** `deinit()`，四处调用点加 `defer w.deinit()`。

幂等**不能**靠「再 deinit 一次空表」：`std.ArrayList.deinit` 的收尾是 **`self.* = undefined`**，
再读 `items` 就是在读 undefined。用 `file_open` / `buffers_live` 两个标志位拦住。

## P1-3　`push` 里的 `try f(try g())` —— 被新用例当场抓出

```zig
try self.entries.append(self.alloc, .{ .key = try self.alloc.dupe(u8, key) });
```

`dupe` 成功（分配 4 字节）、`append` 失败（OOM）时，那 4 字节**没有任何人持有**。

加 `checkAllAllocationFailures` 用例后第一次跑就报：

```
fail_index: 1/8
allocated bytes: 4, freed bytes: 0
[SafeAllocator] leaked [len: 4] allocated at: std.mem.Allocator.dupe
  segment.zig:115  .key = try self.alloc.dupe(u8, key),
```

**修**：分两步 + `errdefer free(k)`。

## P1-4　同一模式在另外三处也存在（顺手修）

搜 `append/put(... try ...dupe ...)` 找到 5 处，都是「内层分配成功、外层容器操作失败」的同类泄漏：

| 文件 | 行 | 修法 |
|---|---|---|
| `catalog.zig` | 117 `names.append(alloc, try alloc.dupe(...))` | 分两步 + errdefer |
| `engine.zig` | 63 / 131 `tables.put(try alloc.dupe(...), ...)` | 同上 |
| `exec.zig` | 195 / 201 `columns.append(alloc, try alloc.dupe(...))` | 同上 |

`sql.zig` 里的同形态用的是 **arena**（整体释放），不受影响。

## P2-1　`del_buf: [512]u8` + `catch continue` 是静默吞错

`base_path` 很长时 `bufPrint` 会 `NoSpaceLeft`，`continue` 让**旧段文件永不删除且毫无提示**。
**修**：改用 `std.fs.max_path_bytes`。

## 测试缺口（记录，不假装覆盖）

`maybeAutoCompact` 的 `catch` 分支**仍未被执行过**：「连续失败 5 次停手」的用例是靠
直接赋值 `auto_compact_fails` 伪造的。要真正覆盖，需要能注入 IO 失败的 mock 文件系统
（比如让 `archiveAppend` 的 `sync` 失败）。当前没有 mock 层，**不将其算作已覆盖**。
