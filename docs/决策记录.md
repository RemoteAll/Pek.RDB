## 2026-10-31（一）建仓与设计口径

### 用户原话

> 「你做为全球最厉害的工程师也是我的助理，现在要协助我使用Rust开发一款一体化数据引擎。通过裁剪大量冷门能力（如存储过程/触发器/窗口函数等），换取更高的读写性能与更低的运维成本；数据量逻辑上无上限（受磁盘与切分策略约束），可替代 SQLite/MySQL/Redis/TDengine 在特定场景的使用。」

> 「我的需求不一定是对或者是准确的，但你可以基于你的理解来帮我先形成文档，然后再根据这个文档实现功能。」

> 「可以参考 NewLife.NovaDb/README.zh-CN.md at master · NewLifeX/NewLife.NovaDb · GitHub，但我并不认为这个项目的实现是很好很高效的。」

### 决策

1. **先文档、后实现**：产出 `docs/架构设计.md` 作为唯一设计口径（磁盘格式写到字节级 + 里程碑 M1~M6），代码按文档落地。
2. **不照抄 NovaDb 的"全表 SkipList 常驻 + 冷数据卸 MMF"**：改为
   **SkipList 只做 memtable → 落盘为不可变有序段（`.data` + `.idx`）→ 内存只留稀疏索引 + Bloom + 块缓存**。
   理由：全表 SkipList 指针开销 ≥ 24B/行（10⁸ 行数 GB），且原地更新带来随机写；段式布局顺序写、内存可硬上限、
   崩溃恢复只需重放 WAL。（NovaDb 的能力边界照借，实现重做。）
3. **MVCC 只做单表事务（Read Committed）**：可见性水位按表维护，`write_mutex` 单表串行、跨表并行；
   **跨表强一致事务明确不做**（写进非目标），避免全局提交锁拖垮写吞吐。
4. **网络协议生态优先**：主推复用 `Pek.RCode` 的 `DbService`（`/Db/*` + DbTable v3 二进制），现有项目只改连接串；
   自有 TCP 帧协议承载高吞吐与复制通道；MySQL 线协议列为可选 feature（v0.3）。
5. **纯 Rust 依赖**：仅允许 `crc32fast` / `memmap2` / `lz4_flex` 一类；不引入 C/C++ 库，保证 zig 交叉编译 musl。

### 验证

- 设计文档落盘：`docs/架构设计.md`（含 §2 与 NovaDb 的逐项差异、§5 字节级格式、§16 性能目标与实测口径）。

## 2026-10-31（三）集群章节补全

### 用户原话

> 「文档上集群相关的描述怎么没有？」

### 事实核对

原 §12 只有 7 行（一张图 + 5 条要点），**不是缺失，但严重不足**：没有 binlog 与 WAL 的区别、没有全量/增量同步流程、
没有一致性语义分级、没有切主步骤与防脑裂、没有分片约定与带宽预算。等价于"提了一句"，无法据此实现。

### 决策

把 §12 扩成完整章节（§12.1~§12.10）：

1. **三种集群形态**：单库一主多从 / 多库分片 / 组合；明确**引擎只做单库主从，分片归路由层**（不引入分布式事务）。
2. **binlog 与 WAL 分离**（不同文件、不同生命周期）：`lsn` 与 `seq` 同一写锁内分配，保证复制序=提交序；
   `binlog/{first}-{last}.blog` 滚动 + `binlog.index` 支持任意位点续传。
3. **全量同步 = 流式拷贝不可变段**（`SnapshotBarrier` 记 `snapshot_lsn`，与增量无缝衔接，从库落地后校验 CRC）。
4. **一致性分级写清**：异步（默认）/ READ YOUR WRITES（`min_lsn` 等待，超时报错）/ **不做同步强一致**。
5. **切主人工化 + `epoch` 防脑裂**：旧主恢复必须 `demote` 否则拒绝写入；**不做自动选主/多主/2PC**。
6. **分片约定**：分片键必须在主键首位；跨分片查询由路由层聚合；扩容用双写回填（M7）。
7. **资源预算**（按全局惯例自检）：增量按批、心跳 5s < 100B、位点 100 批/1s 一次原子写、全量同步限速。
8. 配置样例（`[Replication]`）、观测（`_sys.replication` / `-status` 一行）、里程碑 M5 细化为 5 项、M7 分片工具。
9. 待定问题改为可拍板的 6 条（集群事务语义、切主方式、分片路由归属等）。

### 验证

- `docs/架构设计.md` §12 由 7 行扩至约 130 行，`grep` 检查 `lsn|epoch|binlog|replica.json` 均有落地描述。

## 2026-10-31（四）三条待定项拍板 + 与 SQLite 的性能口径

### 用户原话

> 「我不确定要拍板的三条要怎么弄，你可以帮我推荐。另外我们有可能实现比sqlite性能更好或者同等性能的么？」

### 决策（推荐即定稿，已写回架构文档 §18.1）

| # | 决策 | 理由 |
|---|---|---|
| 1 | **默认异步复制；READ YOUR WRITES 作为可选能力** | 默认零成本；`lsn` 本来就存在，实现只是"读从库时带上 `min_lsn` 并等待"，不改变主路径 |
| 2 | **人工脚本化切主，不做自动选主** | 选主/共识是独立工程且误判代价高；脚本 + `epoch` 防脑裂可审计、可回退 |
| 3 | **分片路由放 `Pek.RDbProxy`**，引擎只守"分片键必须在主键首位"的约束 | 路由逻辑不复制到每个项目；代理侧连接管理已存在 |
| 4 | **从库一律只读**（`AllowWrites=false` 默认） | 多主/双向写需冲突合并，超出 v0.x 目标 |

### 性能立场（§16.2）

- **不承诺"全面超过 SQLite"**：SQLite 是 C + 二十年 B-tree/WAL 优化，点查点写是它的主场。
- 目标：**目标场景同等或更好**——批量追加写 2–5×、多表并发写 3–10×、时序写入数量级领先；点查持平（±30%）；
  随机原地更新暂时落后（约 0.5×），靠后续 `in_place` 热表模式补。
- **不输的 5 件硬事**：块内二分、块大小可配（默认 16KiB）、稀疏索引紧凑化、点查零拷贝、组提交 + `insert_batch`。
- 对比基准放 `tools/bench-vs-sqlite/`（独立 crate，不进引擎依赖树），仓库只提交脚本与结果 CSV；
  **未实测前不写任何数字进 README**（沿用 2026-10-29「不能猜」）。

### 验证

- `docs/架构设计.md` §16.2 新增「与 SQLite 的对比口径（诚实版）」；§18 拆为「已定 / 仍待定」；

## 2026-10-31（五）KV 与 Redis 的性能口径

### 用户原话

> 「那KV和Redis比性能能同等或者超越么？」

### 结论（已写入 §16.3）

- **不做"全面超过 Redis"**：全内存、亚毫秒 p99、丰富数据结构是它的主场；我们只比键值语义（GET/SET/DEL/EXISTS/INCR/TTL/MGET/MSET/SCAN）。
- **"同等"可达**：热数据 + 小值 + 流水线场景（RTT 主导），前提是小值内联进索引、读不落盘。
- **"超越"只出现在 Redis 不擅长的维度**：数据量超过物理内存、持久化无尖刺、多核并行写（Redis 单实例单线程）、成本/GB、内存占用。
- **明确会输**：冷值随机读（要走磁盘 IO）、复杂数据结构（不提供）。

### 为达成"不输"新增的设计约束

1. KV 按 key 哈希分 **16 个日志分片**（各片独立锁/WAL/索引）→ 多核并行写；`SCAN` 分片轮询。
2. **小值内联**（`value ≤ 64B` 驻留内存索引）。
3. 新增 **§11.5 RESP2 子集 + 流水线**：现有 Redis 客户端改端口即可用（不做 pubsub/eval/MULTI/RESP3）。
4. 索引紧凑 + `.hint` 顺序加载（mmap），不重放全日志。
5. 基准 `tools/bench-vs-redis/`（独立 crate，只出 CSV，未实测不写数字）。

### 验证

- `docs/架构设计.md` §10 重写（分片/内联/hint）、§11.5 新增、§16.3 新增、M3 里程碑补充。

## 2026-10-31（六）对比方法论纠正：强项对强项

### 用户原话

> 「对比比的就是各个库的强项。」

### 前一版错在哪

上一轮把「Redis 主场不硬碰」「SQLite 点查不承诺超越」写成了口径，实质是**避开了对手最强的地方**。
用户指出：对比的意义就是拿对手的**强项**来比自己——在强项上落后就不是"取舍"，而是"没做到"。

### 纠正后的口径（§16.1 新增，§16.2/§16.3 改写）

1. **每个对手按它的最佳配置在它的强项上对标**：
   SQLite = WAL + `synchronous=NORMAL` + 预编译语句；Redis = 全内存 + 典型流水线；TDengine = 高频写入 + 时间桶聚合；MySQL = 多连接 OLTP。
2. **达标线硬性**（不达标不算里程碑完成）：
   - SQLite 点查/点写/小事务 ≥ 0.9×；事务批量写 ≥ 1.5×；随机原地 UPDATE ≥ 0.9×（M2 `in_place` 后）
   - Redis 热值 GET p99 ≤ 1.2×、流水线吞吐 ≥ 0.9×、INCR ≥ 0.9×
   - TDengine 写入/时间聚合 ≥ 0.8×（M3）；MySQL 16 并发 OLTP ≥ 1.0×（M4）
3. **落后必须写明**「差距 X% / 原因 / 计划版本」，不允许用"不在对比范围"回避；能力缺失（Redis list/hash/zset）单独标 N/A，不算性能结论。
4. 达不到就改实现（块大小、块内二分、`in_place`、小值内联、协议批量化），不改口径。

### 验证

- §16.1 新增方法论与达标线表；§16.2/§16.3 的"持平/略差/更差"全部改为**可验收的倍数**；M1/M2 里程碑加入基准验收项。

## 2026-10-31（七）语言选型答疑：Zig 能不能"同等或超越"

### 用户原话

> 「那如果用ziglang开发的话能同等或者超越么？」

### 结论

**保持 Rust。换 Zig 不是性能杠杆，收益上限约 ±10–15%，代价远大于收益。**

理由（已写入 §16.4）：

1. **语言不是瓶颈**：Rust 与 Zig 同为 LLVM 后端、同为无 GC 原生语言；SQLite/Redis 的强项来自数据结构与缓存调优，
   不是"用 C 写"这件事。同架构下两者机器码差距通常在 ±10% 量级。
2. **Zig 可能的微优势有限**：`ReleaseFast` 关边界检查、显式分配器/arena 更顺手、`@Vector` 与 io_uring 更直接——
   但这些在 Rust 侧用 `get_unchecked`/自定义分配器/`std::arch`/裸 syscall 同样能做，实测差距常 <10%。
3. **Zig 的代价是决定性的**：
   - **放弃现有复用资产**：`dhrust`（io/logs/net/config）、`Pek.RCode`（SqlSession/DbService）、`serde`/`crc32fast`/`memmap2`
     全部要重写或绑 C，**直接违反"纯 Rust 依赖"约束**；
   - **安全风险**：存储引擎手工内存管理，错一处就是数据损坏；
   - **成熟度**：Zig 0.17 未到 1.0，标准库仍在变；
   - **交付周期**：M1~M4 基本重写，至少多 2–3 个里程碑。
4. **达标路径不变**：块内二分、块大小、`in_place`、小值内联、分片、组提交、协议批量化，与语言无关。

### 重新评估触发条件（三条同时满足才考虑）

① M1 完成 5 件硬事后，SQLite 点查仍 <0.9×；
② `perf` 证明瓶颈是语言级开销（边界检查/分配器/代码布局），且 Rust 侧手段无法消除；
③ 只把该热模块重写为 Zig 并保持 C-ABI 边界（先放宽"纯 Rust 依赖"约束并记录理由），**不改整体技术栈**。

### 验证

- `docs/架构设计.md` 新增 §16.4「语言选型对性能的影响（Rust vs Zig）」。

## 2026-10-31（十一）差距解释 + SQL 执行层接通

### 用户原话

> 「请继续，而且我怎么看这个差距这么大的」

### 差距解释（不是同一层比较）

1. SQLite 测的是**完整 SQL 路径**（VDBE + 每语句事务 + WAL 帧 + 约束 + B-tree 游标）；
2. Zig 侧测的是**裸存储 API**（编码 + WAL + memtable），没有解析/事务状态机/SQL 语义；
3. 同层对比看**批量写**：179.8 万 vs 203.9 万（1.13×），这才是可比的；
4. 点查也不同层：Zig 段整段在内存，SQLite 走页缓存 + 预编译 + 每行分配；
5. 必须做 **SQL 对 SQL** 同层对比，且 PK 等值查询要走点查快路径，否则是自欺。

### 本轮代码

## 2026-10-31（十九）8KB / RISC-V 小内存可行性（实测，不猜）

### 用户原话

### 一、做了什么（不是估算，是跑出来的）

1. **新增 `zig build sizes`**（`src/sizes.zig`）：打印 `@sizeOf` 真实布局，`metric,item,bytes` 格式。

2. **双指针宽度测量**：本机 64 位 + `-Dtarget=x86-windows` 32 位（与 RISC-V/Cortex-M 同指针宽度）。
   原始结果入库：`docs/实测数据/嵌入式-2026-10-31.csv`。
3. **新增 `zig build check`**（`addObject`，不链接不需 entry），**`-Dtarget=riscv32-freestanding -Doptimize=ReleaseSmall` 编译通过**。

### 二、实测数据（32 位）

`skiplist.Node=80`、`table.Table=248`、`segment.Segment=136`、`segment.IndexEntry=16`、
`wal.Wal=56`、`skiplist.Skiplist=104`、`sql.Value=16`、`codec.CRC_TABLE_BYTES=1024`（常量区）。

### 三、结论

- **8 KB RAM：现在的引擎不行**。固定项就 544B，`flush_bytes=4KB` 只能容纳约 30~40 个 key
  （Node 80B + key/value 副本），再加索引项、Bloom（1.25B/key，当前关不掉）、栈与堆开销必然超 8KB。
  要上 8KB 必须做 **M0 档**：无 memtable、无 Bloom、无 mmap/线程、单页 512B 缓存、固定池（工作量 = 重写存储层，不是加开关）。
- **16–64 KB：能跑 KV-only**（关 SQL/Bloom/线程，`flush_bytes≈4KB`，数据集几千条）。
- **128KB–1MB 的 riscv32 MCU（ESP32-C3、CH32V307 等）：可用（C 档）**。32KB memtable ≈ 250 key 常驻；
  数据集超过 memtable 后每 key 只留 ~1.5B 索引+Bloom。
- **≥8MB RTOS/Linux：B 档可用（SQL 子集）**；**≥64MB riscv64 小主机：全功能**（需重编，不改架构）。
- **硬下限**：索引项 0.25B/key + Bloom 1.25B/key 是「每 key 常数」，决定「小内存 + 大数据」的上限。

### 四、RISC-V 特有约束（读代码得出，已写入 §16.5.7）

无 MMU 的 riscv32 不能 mmap（改 `read_at` + 页缓存）；`std.Io.Threaded` 需 OS（裸机单线程）；
rv32ec 无原子指令需禁 64 位原子（单写者约束已满足）；CRC 表 1KB 常量换 64B 半字节表。

### 五、尚未实测（明确标注，不当结论）

- **flash 字节数**：需完整链接 + 解析 ELF 段大小，下一轮做 `mcu_probe.zig` + `tools/elf-size.py`。
- **栈水位 / heap 峰值**：需 QEMU riscv32 或真板子跑一轮。

### 六、下一步

1. M8 骨架：`build.zig` 加 `-Dembed=<A|B|C>` 裁剪开关 + `tools/elf-size.py` 出 flash 报告。
2. 若确认要冲 8KB：单独立项 **M0 档**（无 memtable 的「直接追加 + 按需读索引」存储层）。

## 2026-10-31（二十）M0 档落地：8KB 级嵌入式 KV（已实现 + 已实测）

### 用户原话

> 「**8KB 档需要另做 M0 档重写存储层** 这个可以弄么？我能够能够用在各种嵌入式系统和低资源的设备中，最好是能通用复用的」

### 一、已实现（`spike-zig/src/m0.zig`，5 个用例）

- **API**：`Store.open(dev, cfg, scratch)` / `put(k, v, scratch)` / `get(k, out, scratch)` / `del` / `eraseAll` / `usedBytes`。
- **零分配**：没有任何 allocator；缓冲由调用方给（1 扇区 + 1 记录）。
- **块设备抽象**：`BlockDevice{ ctx, vtable{read,write,erase,sync}, capacity, sector_size }` ——
  NOR/NAND Flash、SD、EEPROM、内存盘都能接，**不绑定 OS/文件系统**，这是「通用复用」的落点。
- **布局**：key 哈希分区（分区数 comptime，2 的幂）→ 每分区一条追加日志；`get` 只读该分区。
- **记录**：`[op][klen][vlen][key][value][crc32]`，不跨扇区；墓碑删除。
- **自愈**：上电扫描每个分区定位追加点；坏记录/填充 → 该扇区剩余不可写（NOR 只能 1→0），追加点移到下一扇区。

### 二、实测（riscv32-freestanding / ReleaseSmall / strip）

`zig build mcu -Dtarget=riscv32-freestanding -Doptimize=ReleaseSmall` → `tools/elf-size.py`：

| 项 | 字节 |
|---|---|
| `.text` | **1,540** |
| `.rodata` | **1,056**（其中 1,024 = CRC32 查表） |
| `.eh_frame*` | 408（可 `-fno-unwind-tables` 去掉，待验证） |
| **flash 合计** | **3,004** |
| `m0.Store`（@sizeOf） | **96** |
| 引擎自身静态 RAM | **640**（= .bss 16,896 − 16,384 伪 Flash） |

原始数据：`docs/实测数据/嵌入式-m0-2026-10-31.csv`。

**结论：8KB RAM 设备可用（4KB 也有余量）**，数据集上限由 Flash 与分区划分决定，不再由 RAM 决定。

### 三、过程中被实测打出的 bug（值得记）

第一版 `open` 把追加点设成「最后一条合法记录末尾」，撕裂尾测试立刻失败：
`writeImpl` 报 NOR 写入冲突（`cur & b != b`）——因为掉电时那几个字节已经被编程过，**不能再写**。
修法：遇到坏记录/填充，追加点直接跳到**下一个扇区边界**，并让扇区尾部留一个 0x00 标记（让扫描知道本扇区到这儿为止）。
**如果没有「撕裂尾」这个用例，这个 bug 只会在真机掉电后才暴露。**

### 四、尚未做

1. 压缩：写满返回 `Error.NoSpace`（可预测，不静默丢数据）；计划 A/B 影子区流式重写。
2. CRC 半字节表：flash 1,024B → 64B。
3. 真实 SPI NOR 驱动 + 掉电实测。
4. 栈水位实测（QEMU riscv32 / 真板子）。

## 2026-10-31（二十一）极小档：百字节级 RAM（M0-tiny）

### 用户原话

> 「那是不是也能支持很小很小字节数的」（附 4/8/16/32 位 MCU 的典型 RAM 表：4 位几十~几百字节、8 位 128B~2KB、16 位 1~8KB、低端 32 位 2~8KB）

### 一、改了什么

1. **容量编译期化**：`Store` 改为 `StoreType(comptime max_parts, comptime crc_kind)`；
   `Store = StoreType(8, .table)`、`TinyStore = StoreType(2, .bitwise)`。
2. **CRC 三档**：`codec.crc32`（1KB 表）/ `crc32Nibble`（64B）/ `crc32Bitwise`（0B）。
3. 新增用例「极小档（2 分区 / 32B 扇区 / 无表 CRC）在 512B 存储上可用」，含 RAM 预算断言。

### 二、实测

| 项 | 数值 |
|---|---|
| `m0.TinyStore`（32 位） | **32 B** |
| 引擎自身 RAM（Store + 32B 扇区 + 24B 记录） | **88 B** |
| flash（riscv32 / ReleaseSmall / strip） | **1,610 B**（.text 1,282 + .rodata 24 + .eh_frame 304） |
| flash（thumb / Cortex-M0） | **1,370 B**（.text 1,206 + .rodata 52） |

多目标：`check`（对象编译）对 riscv32 / thumb / **avr** / **msp430** 全部通过；
完整链接 avr 与 msp430 均失败于 `sub-compilation of compiler_rt failed`（Zig 0.17 的 compiler_rt 不支持这两个后端），
**不是本代码的问题**——已如实写进 §16.5.9，不吹成「支持 AVR」。

### 三、本次最有价值的教训（又被打脸一次）

第一版把 CRC 做成 `Config.crc` **运行期**枚举。看着没问题，实测 `.rodata` = **1,117B** ——
因为三个 CRC 实现（含 1KB 全表）都被链接进去了，switch 只是运行期选择。
改成 comptime 参数后 `.rodata` 掉到 **24B / 52B**，flash 从 2,855B 降到 1,610B。

这正是 §16.5.1 第 1 条「能力必须*编译期*关闭，关掉后零代码零内存开销」的反例与验证：
**运行期开关 ≠ 裁剪**。以后凡是「可裁剪」的功能，一律 comptime 参数，不得用 runtime enum/bool。

### 四、结论（对应用户的 RAM 分档）

- 低端 32 位（2–8KB RAM）：**可直接用**（88B RAM + 1.4KB flash）。
- 8 位 AVR / 16 位 MSP430（128B–2KB）：**代码可编译**，但当前 Zig 0.17 链接不了；
  等 Zig 修 compiler_rt，或改用外部工具链交叉验证。
- 仍属「待实测」：真机运行、栈水位、SPI NOR 掉电行为。

## 2026-10-31（二十二）M0 压缩：分区改为环形日志（写满不再是终点）

### 背景

上一轮 `put` 写满分区直接 `Error.NoSpace`。512B 存储 + 2 分区时，十几次写入就满 ——
对嵌入式真实使用场景等于不可用。这轮把它补上。

### 一、改法

1. **分区变环形日志**：新增 `tail_at[]`（每分区存活区起点扇区），`rawAppend` 在尾部放不下时
   **回卷到分区头**（前提：`slot + len <= tail`，绝不覆盖存活区）。
2. **`compact(p, scratch)`**：按**环序**从最旧扇区开始，把「环序上后面没有同 key 更新记录」的记录
   搬到追加点，然后擦掉旧扇区。`compactAll` 逐分区执行。
3. **`hasNewer` 用环序距离**：`dist(record, from) < dist(append, from)` 即算「更新」——
   回卷后新旧判定仍正确，不需要额外状态。
4. **`get` 改按「距 tail 的距离」取最新**：回卷后线性扫描顺序不再等于时间顺序，这是必须改的。
5. **`scanPartition` 不再遇空扇区 break**：压缩后分区中间会出现空洞，必须全分区扫描并取最大有效尾。

### 二、过程中的三个真 bug（都是测试打出来的）

1. **回卷踩活数据**：只判断 `slot < tail` 不够，`tail == start`（写满未压缩）时回卷到 0 会覆盖已有记录 →
   NOR 直接 `DeviceFailure`。改成必须满足 `slot + len <= tail`。
2. **填充标记踩记录**：跨扇区时无条件写 `at-1 = 0x00`，若上个扇区正好写满，那个字节属于上一条记录 →
   写失败。改成仅当「确实跳过了扇区剩余」（`append % ssize != 0`）才写标记。
3. **空分区 tail 不更新**：`tail` 初始为 `partitionEnd`（表示空），但第一条记录写入后没更新，
   导致后续回卷判定认为「没有存活区」→ 覆盖数据。修：首条写入时把 tail 设为其所在扇区起点。

### 三、实测（riscv32 / thumb，ReleaseSmall / strip）

| 项 | 压缩前 | 压缩后 |
|---|---|---|
| riscv32 flash | 1,610 B | **1,976 B**（+366） |
| thumb flash | 1,370 B | **1,810 B**（+440） |
| `TinyStore`（32 位） | 32 B | **40 B**（+`tail_at[2]`） |
| 引擎 RAM（tiny） | 88 B | **96 B** |

即：**多花 ~370B flash / 8B RAM，换来「写满后可回收继续用」**。仍远在 2KB RAM 设备余量内。

### 四、仍待办

- `compact` 的存活判定是「全分区扫描 × 每条记录」，O(记录数 × 扇区数)；小分区可接受，
  大分区要加按扇区的存活位图（M0-v2）。
- 真实 SPI NOR 驱动、真机掉电、栈水位实测。

  1. 610B 记录（必跨 256B 页）写入 → 读出逐字节一致，`violations == 0`，`pp_count >= 3`；

### 二、被自检打出的真 bug：压缩在「满」的时候必然失败

自检的「写满 → 压缩 → 继续写」直接把老实现打挂（`NoSpace`）：
**压缩要把存活记录搬到追加点，但追加点就在分区末尾——没有空间可搬。**

改成**原地游标式压缩**：读位置从 `tail` 走一整圈，写位置紧跟其后（永不越过读位置），
每个扇区「先读进缓冲 → 擦掉 → 把存活记录写到写游标」，完成后 `append_at = 写游标`。
这样**不需要任何额外空闲空间**，也不会覆盖未读数据。存活判定改为「环序窗口 `(abs, append)` 内是否有同 key」，
忽略已处理区域。

> 顺带记：这个 bug 只有在「分区真的写满」时才会出现，前面的用例都是「写一些 → 压缩 → 还有空间」，
> 所以一直没暴露。**自检用例的价值就在这里。**

## 2026-10-31（二十五）压缩存活索引：O(记录数×扇区数) → O(记录数+扇区数)

### 用户原话

> 「目前没法真板实测，现在继续往下做 1. 大分区存活位图（`compact` 目前 O(记录数×扇区数)），然后再回到主引擎线」

### 一、做法

`compact` 的瓶颈是**每条记录都要扫全分区**判断「后面有没有同 key 更新」。改为：

1. **一趟建索引**：从 `tail` 按环序扫一遍，把每个 key 的**最大环序距离**（= 最新版本）记进调用方给的索引区；
   槽位结构 `key[8] + dist(u32) + klen(u8) + used(u8)`，固定 16 字节/槽（`std.mem.readInt` 读写，不依赖对齐）。
2. **第二趟判定**：每条记录 O(1) 查索引，`dist == 索引里的最大 dist` 即存活。
3. **自动退路**：索引槽位 < 8 或 `key_max > 8` → 直接走原来的扫描路径（结果一致）。
   这保证小 RAM 设备（scratch 只有 2 个扇区）行为不变。
4. 诊断位：`m0.last_compact_indexed` 标记上一次走哪条路径，用例靠它断言两条路径都被真正跑到。

`scratch` 布局：`[0,ssize)` 读缓冲、`[ssize,2*ssize)` 查重缓冲、`[2*ssize,...)` 索引区。
索引区大小 = 4KB 分区 / 40B 记录 ≈ 100 条 → 给 **1.6KB 索引**（100 × 16B）即可全覆盖。

### 二、验证

- 新增用例：「压缩走索引快路径，且与扫描路径结果一致」——先用大 scratch（含 32 槽）压实并断言 `last_compact_indexed == true`，
  再用最小 scratch 压实并断言 `== false`，两次结果逐 key 比对一致，最后掉电重开再比一次。
- **37 个用例全绿**；尺寸未变：`TinyStore` 40B、引擎 RAM 96B、flash riscv32 **1,976B** / thumb **1,810B**
  （全局诊断位只占 1B .bss）。

### 三、下一步

用户已明确：压缩优化收尾后**回到主引擎线**——§16.1 达标线还差「并发写」与「超内存数据集」两项实测。

## 2026-10-31（二十六）回到主引擎线：并发写 + 超内存数据集（已实测）

### 用户原话

> 「请继续」（承上一轮：「大分区存活位图…然后再回到主引擎线」）

### 一、本轮做了什么

在 `spike-bench` 里加两组此前缺的场景（架构 §16.1 达标线要求）：

1. **并发写（跨表并行）**：1/2/4 线程各持独立 Table，每线程 30 万行；测总吞吐与扩展比。
   （架构口径是「单表串行、跨表并行」，`Table` 本身没有锁，**同表多线程不是支持用法**。）
2. **超内存数据集**：200 万行、`flush_bytes=8MB` → 稳定 25 个段；测写入、随机点查、范围扫描、冷重开。

### 三、观察（不是结论，待下轮验证）

- **4 线程只有 2.42×**：主要瓶颈疑似 WAL 组提交的 `fsync`（每 1 万批一次）与磁盘本身；
  要给出结论必须在 `wal_sync_every` 与线程数上做交叉实测。
- **点查掉到 46%**：25 个段就是 25 次 Bloom + 最坏 25 次块读。可行优化方向：段级布隆加「前缀区间」快速跳过、
  或 compaction 合并小段。**先量再改**。
- **写类指标波动 5–15 倍**：本机存在后台磁盘/杀毒干扰。仍按纪律取中位 + 记录 min–max；
  后续需要在安静窗口复测才能报更稳的数字。

### 一、本轮做了什么

给上一轮新增的两组场景补上 SQLite 对照（`tools/bench-vs-sqlite`）：

- **并发写**：每线程独立库文件（与 Zig 侧「每线程独立 Table」公平对齐），两种形态都测：
  (a) 逐行 autocommit（对应 Zig 逐行 put）；(b) 每线程单事务（SQLite 最佳形态）。
- **超内存数据集**：200 万行单事务建表 → 10 万次随机点查 → 1 万行范围扫描 → 关闭重开。
- `tools/compare-bench.ps1` 增加这 6 组对比口径，重新生成 `docs/实测数据/对比-2026-10-31.md`。

### 三、达标线结论（§16.1 第 4 条）

- SQLite 点查 ≥0.9×：**达标**（5.7×）
- SQLite 点写 / 小事务 ≥0.9×：**达标**（65×）
- SQLite 事务内批量写 ≥1.5×：**达标**（7.10×，注：SQLite `put_txn` 本机波动极大 213K–1.05M）
- MySQL 16 连接并发 ≥1.0×：属 M4，**未测**
- **冷重开不在达标线里，但差距必须写明**：慢 4.6–7.8 倍。原因是 200 万行要加载 25 个段的稀疏索引 + Bloom。
  优化方向（下轮候选）：段 meta 合并成单文件、索引页懒加载。这是真实弱项，不粉饰。

### 四、仍存在的测量风险

写类指标本机波动 5–15 倍（后台磁盘/杀毒）。本轮用「Zig 6 轮 + SQLite 3 轮取中位」压制，
但后续若要报更硬的数字，需要在安静窗口复测并把机器状态一并记录。
