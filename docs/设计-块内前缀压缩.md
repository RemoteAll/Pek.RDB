# 块内公共前缀压缩 · 设计、实现与实测（2026-11-01）

> 目标（用户原话）：**「各方面的数据要和 sqlite 同等或者超越而不是降低」**
> 改动前唯一未达标项：磁盘 **48.56 vs 41.56 B/行（+17%）**。
> **本轮结果：40.92 B/行（比 SQLite 低 1.5%）**，吞吐项同批对比无一项落后。

## 一、为什么不用「逐条前缀压缩」

逐条存 `pfx` 需要每行 1 字节，8 字节 key 只压到 `1(pfx) + 2(suffix) = 3`，净省 5 B。
如果改成**块内统一公共前缀**（块头存一次），行内只需 suffix，8 字节 key 压到 2 B，净省 **6 B**，
而且块头摊销后只有 1 B / 64 行 = **0.016 B/行**。
（§16.1.27 的探针已实测「逐条前缀压缩」解码 −8.3%，本方案不是它的变体。）

## 二、落地格式（`PEKZAG07` / `PEKZIX05`）

**块 = 64 行**，与稀疏索引的 `INDEX_STRIDE` 对齐，每个稀疏索引项的 `offset`
改指**块头**而不是首条记录。

```
块   = [ u8 pfx_len ]  [ 记录 × 最多 64 条 ]
记录 = u8 klen | u8 vlen | u32 (seq | 墓碑<<31) | key[klen - pfx_len] | value[vlen]
```

- **块内第 1 条记录存完整 key**，它同时充当本块后续记录的前缀来源 → **块自描述**。
  这一点与最初设计不同：原打算「块首 key 从稀疏索引取、块里不存」，
  但**顺序迭代会跨块**（`MergeIter` 一路往后扫），那时没有索引项可查，前缀就没有来源。
  存一份进块只多 **8 B / 64 行 = 0.125 B/行**，换来「可独立迭代、不依赖索引」。
- `pfx_len == 0`（随机 key，块内无公共前缀）→ 每条都存完整 key，**读路径零拷贝**，
  随机 key 场景完全不退化。
- `pfx_len > 0` → 第 2 条起只存 `key[pfx_len..]`。

## 三、行头 17 → 7 → 6 字节

| 版本 | 布局 | 字节 |
|---|---|---|
| `PEKZAG04` 及更早 | `klen4 + vlen4 + seq8 + flags1` | 17 |
| `PEKZAG05`（§16.1.26） | `klen1 + vlen1 + seq4 + flags1` + 哨兵逃逸 | 7 |
| `PEKZAG07`（本轮） | `klen1 + vlen1 + u32(seq \| 墓碑<<31)` + 哨兵逃逸 | **6** |

墓碑位挂到 `seq` 最高位：全项目 `flags` 只用到 bit0（0 正常 / 1 墓碑），
所以 `seq` 原地可用区间从 2³² 降到 **2³¹−1**（21 亿次写入，超了走既有逃逸），
换来每行 1 字节。`flags` 带 bit0 以外的位时也走逃逸（信息不丢，有用例守住）。

## 四、读路径与「别名」这个坑

`codec.RecIter`（段内行迭代器）：
- 进新块：读 1 字节 `pfx_len`，用 `pfx=0` 解出**块首完整 key**，记为 `base`；
- 块内其余行：`readRec` 只给 suffix，拼成 `base[0..pfx] ++ suffix`；
- 拼装落**双缓冲**：第 n 行写 `buf[n&1]`，覆盖的是第 n−2 行，而「上一行」在第 n−1 行的另一块上
  → 调用方回看**一行**永远安全。

**双缓冲的边界必须写清楚**：`MergeIter.last_key` 是「上一个**产出**」的 key，
可能距当前行 2 行以上（同 key 多版本被跳过时），双缓冲会轮回到同一个 buf →
比较退化成「自己和自己比」→ 误判重复 → **整行丢失**。
所以 `MergeIter` 用 `last_buf`（容量按段头 `max_klen` 预留）存稳定副本；
`Segment.scanRefs` 改成「只和**上一行**比」（等价语义，回看距离恒为 1）。

**收集型 API 的 key 有效期**：`Table.scanRefs` / `Segment.scanRefs` 把记录收集起来、
交给调用方**之后**才读，key 必须落成稳定内存 → 用**分块 `KeyArena`**（块分配后不移动，一遍过）。
第一版写成 `ArrayList(u8)` + 「先记偏移、最后回填」，第二遍遍历 96MB 输出数组
把 `scan_refs` 从 12.2M 打到 9.8M 行/s；分块后连回填也省掉，
并且让 `RecIter` 直接把 key 重建进 arena（`sink`），额外那次 memcpy 也不要了。

## 五、磁盘预算与实际

| 项 | 改动前 | 改动后 |
|---|---|---|
| 记录头 | 7 | **6** |
| key | 8 | **2**（suffix，pfx≈6） |
| value | 32 | 32 |
| 块头 + 块首 key 摊销 | 0 | 0.141 |
| 索引（31250 项 × 20 B） | 0.31 | 0.31 |
| Bloom（10 bit/key） | 1.25 | 1.25 |
| **合计** | **48.56** | **≈41** |

**实测**：`97,127,373 → 81,831,751 B`，即 **48.56 → 40.92 B/行**；
SQLite 同批 `83,111,936 B = 41.56 B/行` → **低 1.5%**。

对账：块内前缀落地后是 83,831,751；再把行头 7→6 后是 `83,831,751 − 2,000,000 = 81,831,751` ✓
恰好每行 1 字节，证明省下的就是行头那一个字节，没有别的角落被顺手改动。

## 六、没做的两项（数据已经够了）

| 方案 | 预估省 | 为什么不做 |
|---|---|---|
| Bloom 10 → 8 bit/key | 0.25 B/行 | 误报率 1%→2%，点查（我们最强的项之一）受害；**本轮已达标，没理由再拿查询换磁盘** |
| 稀疏索引 offset 改 delta varint | 0.14 B/行 | 收益 0.1 B/行却引入变长索引与 seek 复杂度，不划算 |

## 七、验收

1. `big_disk_bytes_row` **40.92 ≤ 41.56** ✓
2. 62/62 单元用例通过；新增用例覆盖：`RecIter` 块内前缀往返、pfx=0 与 pfx>0 混排、
   残块（不满 64 行）、空 key、跳块定位、`flags` 高位走逃逸
3. 同批 3+3 轮吞吐：**18 项可判定、0 项落后**；2 项区间重叠（测不出来）、
   2 项口径不等价（`scan_refs` 收集 48 B/行 vs SQLite 只数行，同口径对照 `range_k_200k` 2.02×）。
   原始 CSV：`docs/实测数据/*-2026-11-01-pfxblk2-run{1,2,3}.csv`；
   完整表见 `docs/决策记录.md`（六十六）。

## 八、没做、但记下来

- `MergeIter` 的 `last_buf` 每产出一行要拷一次 key（8 字节）。理论上可以「只在源缓冲即将被
  复用时才拷」，复杂度不值这个 8 字节 memcpy。
- `pfx_len` 是 1 字节，key 长于 255 时不行 —— 改成 varint 要动块头解析热路径，收益近零。
