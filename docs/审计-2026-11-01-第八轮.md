## 一、P1-1 `Wal.reset()` 的 `written` 清零顺序

### 问题

```zig
// 修改前
try self.file.setLength(self.io, 0);
try self.file.sync(self.io);
self.written = 0;          // ← 太晚
```

`setLength` 成功后文件已经是 0 字节；若紧接着的 `sync` 失败（磁盘满 / IO 错误），错误往上抛，
而 `written` **还停在旧值**（例如 100,000）。下一次 `append` 触发 `flushBuf` 时：

```zig
try self.file.writePositionalAll(self.io, self.buf.items, self.written);  // 从 100,000 开始写
```

→ 文件前 100,000 字节全是空洞（0），重开时 `parseBatches` 在偏移 0 读到长度/CRC 全 0，
**当成撕裂尾直接停止** → 空洞之后的 WAL 全部丢失。

### 修法

```zig
try self.file.setLength(self.io, 0);
self.written = 0;          // 与文件长度保持一致，必须在 sync 之前
try self.file.sync(self.io);
```

### 验证

- 用例 `wal reset：原地截断后文件为 0 字节，旧批次不得被回放` 补了一条不变量断言
  `expectEqual(0, w.written)`。
- **如实记录**：这条断言只在 happy path 生效；真正触发 bug 的 `sync` 失败路径**目前无法用现有 API 构造**
  （与 `maybeAutoCompact` 的 catch 分支同属「需要 mock IO」的缺口）。
  修法的正确性靠「把不变量的建立点放在不可能失败的那一步之后」这一结构保证，不靠用例。

## 三、P1-3（未解决）写路径仍有瞬时变慢 —— 上一轮的说法要纠正

### 3.1 先纠正上一轮的结论

第七十一节写了「**崩塌轮次消失**」「`always-ahead = 22；unresolved = 0`」。
这个结论建立在 `p10` **7 轮全干净**之上。本轮审计追加了三批数据，结果不支持「消失」：

| 批次 | 轮数 | 出现写路径整体变慢的轮次 | 占比 |
|---|---|---|---|
| `p10`（修复后，正式批次） | 7 | 0 | 0% |
| `p11`（审计复核批次） | 3 | 1（r2） | 33% |
| `bare`（裸写探针批次） | 5 | 1（r2） | 20% |
| `segphase`（段写拆分批次） | 5 | 1（r3：`big_put` 0.47×；r4：`put` 0.2×） | 20–40% |

**合计约 1/10 轮次（10–25%）仍会出现。** WAL 轮换那一刀确实去掉了一个**确定**来源
（配对 A/B 7/7、中位 1.35×、`big_put` +41%），但它不是唯一来源。

> 教训：**7 轮全干净不等于问题解决**。判定「消失」需要的最少轮次应由「故障率」反推——
> 若真故障率是 10%，7 轮全过的概率是 0.9⁷ ≈ 48%，等于抛硬币。

### 3.2 已定性：**不是磁盘慢，是我们自己的写路径**（⚠️ 本小节已被后续实验修正，见 §3.6）

本轮新增了「裸文件写探针」（`bareWriteMbPerSec`）：完全不经过引擎，只做
「建文件 → 8MB 分块写 → 每块 fsync」，在基准的**起点 / `big_put` 之后 / `b8_put` 之后**各打一个点。

`bare` 批 r2（该轮 `big_put` = 0.72×、`put` = 0.47×）：

| 指标 | r1（正常） | r2（塌） | r2/r1 |
|---|---|---|---|
| `bare_write_mbps`（起点） | 364 | 343 | 0.94× |
| `put`（只写 WAL，不落段） | 1,912,122 | 889,795 | **0.47×** |
| `get` | 935,933 | 900,167 | 0.96× |
| `scan` | 11,844,131 | 11,362,345 | 0.96× |
| `put_batch` | 1,869,455 | 2,036,613 | 1.09× |
| `sql_put` | 1,727,619 | 1,686,343 | 0.98× |
| `conc_put_4t` | 4,028,567 | 3,983,650 | 0.99× |
| `big_put` | 2,025,998 | 1,467,203 | **0.72×** |
| `bare_write2_mbps`（`big_put` 之后同一时刻） | 351 | 314 | 0.89× |
| `big_get` / `big_count` | 578,732 / 26,385,781 | 536,573 / 25,903,246 | 0.93× / 0.98× |
| `b8_put`（同配置第二次 200 万行） | 2,017,777 | 2,006,047 | 0.99× |
| `bare_write3_mbps` | 344 | 342 | 0.99× |

**三条关键证据**：

1. **裸写正常**（314–343 MB/s，与其他轮一致），引擎写却慢 —— 排除「磁盘/文件系统整体变慢」。
2. **`put` 也慢**（0.47×）—— `put` 用 `flush_bytes = 1GB`，**一次段 flush 都不发生**，
   只有「memtable 插入 + WAL 缓冲追加」。（`Wal` 只有 `flushBuf` 的普通写，无 fsync。）
3. **同一轮、同一配置、同一数据量**：`big_put` 503,836（`p11 r2`）/ 1,467,203（`bare r2`）
   而 `b8_put` 2,006,047 —— 两者代码路径完全一样，只差执行时刻（相隔约 20 秒）。

### 3.3 段写三段拆分（`segphase` 批）

给 `Writer` 加了 `ns_create` / `ns_write` / `ns_sync` 三个计数器：

| 轮 | `put` | `big_put` | 建文件 | 写块 | **fsync** | 段写合计 | 裸写 MB/s |
|---|---|---|---|---|---|---|---|
| r1 | 1,108,881 | 1,953,268 | 8.5ms | 29.7ms | **234.6ms** | 394ms | 126 |
| r2 | 1,696,055 | 1,790,412 | 9.3ms | 30.9ms | **288.5ms** | 453ms | 315 |
| **r3** | 1,833,979 | **880,199** | **42.4ms** | **83.9ms** | **579.0ms** | **1088ms** | 317 |
| r4 | **376,627** | 1,862,879 | 8.7ms | 31.8ms | 271.7ms | 433ms | 349 |
| r5 | 1,890,353 | 1,779,871 | 9.4ms | 33.8ms | 262.9ms | 442ms | 329 |

结论：

- **fsync 是段写的主要成本**（235–288ms / 394–453ms ≈ **60%**），建文件与写块合计只有 ~10%。
- 坏轮次（r3）里三段**一起**变慢（create 4.5×、write 2.5×、sync 2.2×），不是某一个 syscall。
- 坏轮次里 `bare_write2` 仍是 317 MB/s → 又一次排除磁盘。

### 3.4 目前**没有**成立的原因（不许写成结论）

- ❌「Windows Defender 扫新文件」—— 未验证。`b8_put` 同样建 25 个新文件却正常。
- ❌「页缓存/脏页写回」—— 未验证。裸写探针写的是同样规模的数据。
- ❌「`std.Io.Threaded` 线程池被阻塞」—— 未验证，需要看 `std` 的 io 实现。
- ✅ 可以确定的只有：**与文件写入次数/fsync 次数的暴露有关，且与时刻相关**。

### 3.5 待办（下一轮往下推进的方向，按性价比排序）

1. **降 fsync 次数**（fsync 占段写 60%，是最肥的一块）：
   - 索引归档 `archiveAppend` 每 flush 都 `setLength + sync`（25 次）。若数据段已 `sync`，
     归档只需要「记录段边界」，可考虑**组提交**（每 N 次 flush 或每个 checkpoint 刷一次）。
     **前提**：必须先证明「归档落后于段」在崩溃时仍能自愈（现有 `index_valid_len` 从有效末尾
     覆盖残片的机制正好可用）。
   - WAL `reset()` 里的 `setLength + sync`（25 次）同理。
2. **加「时刻」维度**：给每个探针打上「距进程启动的秒数」，坏轮次出现时能判断是
   「固定时刻」还是「随机时刻」。
3. **加进程内文件 IO 计数器**：直接统计每秒的 write/sync 调用次数与耗时，
   而不是靠分段计时反推。

### 3.6 后续实验修正（同日，`fbsize` 批 7 轮）：抖动有**两类**，本节 3.2 的单一结论过窄

接着做「降 fsync 次数」时发现，**裸写探针自己也会崩**：

| 轮 | `bare_write`（起点） | `bare_write2`（`big_put` 后） | `bare_write3`（`b8_put` 后） | `big_put` | `b8_put` | 读指标 |
|---|---|---|---|---|---|---|
| r1–r5, r7 | 257–336 | 246–347 | 225–351 | 1.07M–1.96M | 1.42M–1.97M | 正常 |
| **r6** | **339（正常）** | **27** | **31** | **406,416** | **525,610** | **全部正常** |

r6：裸写 339 → **27 MB/s（降 12 倍）**，整套写指标全崩（`put` 0.53×、`sql_put` 0.27×、`big_put` 0.21×），
而所有读指标正常。

→ 所以准确的说法是**两类抖动**并存，不能一句「不是磁盘慢」概括：

| 类型 | 特征 | 证据 | 对策 |
|---|---|---|---|
| **A 长窗口（环境级）** | 裸写也慢（12×），持续数十秒，读不受影响 | `fbsize` r6 | 代码改不动；只能降总写入量 / 轮次间冷却 / 报告里区分好坏窗口 |
| **B 短脉冲（我们更敏感）** | 裸写采样正常，引擎写慢 2–4× | `bare` r2、`p11` r2 | 我们的文件操作次数远多于裸写探针，更容易撞上；降操作次数有效 |

### 3.7 `flush_bytes` 敏感度实验：**不是解药**

假设：段写 60% 是 fsync，那么加大 `flush_bytes`（25 → 7 → 4 次 flush）应当更快更稳。实测（同进程、同窗口、同 200 万行）：

| 轮 | `big_put`（8MB / 25 次） | `fb32`（32MB / 7 次） | `fb64`（64MB / 4 次） |
|---|---|---|---|
| r1 | 1,656,975 | 1,775,219 | 1,709,592 |
| r2 | 1,935,585 | 2,027,466 | 1,980,819 |
| r3 | 1,072,368 | 930,087 | 1,277,528 |
| r4 | 1,535,563 | 1,958,238 | 1,930,603 |
| r5 | 1,957,741 | 1,278,022 | 1,984,141 |
| **r6** | **406,416** | **544,401** | **534,296** |
| r7 | 1,786,977 | 1,532,392 | 1,859,529 |

结论：

1. **好窗口里三者吞吐基本相同**（约 1.9–2.0M）→ fsync 次数在当前数据量下**不是瓶颈**。
2. **坏窗口（r6）三者一起崩** → 加 `flush_bytes` 不能规避 A 类抖动。
3. 单个轮次里谁快谁慢没有稳定规律（r3 是 fb32 最差、r5 也是 fb32 最差、r7 反过来）→ 是窗口随机命中，不是配置差异。

> **这条否掉了审计待办第 1 项的原计划**：原本打算「降 fsync 次数」来治尾部，实测证明治不了。
> 少做一次无效优化，就少一次「把噪声当成果」的机会。

### 3.8 **更根本的问题：旧跑法有时间窗口偏差，之前「SQLite 同轮正常」的证据全部作废**

用户追问「为什么不直接看 SQLite 源码」时去查了源码，顺带发现旧跑法本身有系统性缺陷：

```
旧跑法 round = [ 我方整套基准 ~18–30s ] → [ SQLite 整套基准 ~25s ]
```

两个引擎**永远不在同一个时间窗口里采样**。而 A 类抖动持续数十秒 ——
它完全可以整段落在我们身上、而我们跑完之后它刚好结束。实测证据（`fbsize` r6）：

| 采样点 | 我方裸写探针 | 说明 |
|---|---|---|
| 基准起点（0s） | **339 MB/s** | 正常 |
| `big_put` 之后（~8s） | **27 MB/s** | **窗口已坏** |
| `b8_put` 之后（~11s） | **31 MB/s** | 仍坏 |
| 整套结束 | ~30s | — |
| SQLite 开跑 | ~30s 之后 | **另一个窗口** |

→ **「SQLite 同轮正常」从来不是「SQLite 免疫」的证据**，它只是跑在另一个窗口里。
本报告 §3.2 与 §3.6 里「SQLite 同轮正常 ⇒ 是我们的问题」的推断**全部作废**。

同时暴露一个自伤行为：加上 `big_put_strong` / `fb32` / `fb64` / `walab` 四组探针后，
**单轮写入量从约 1.0GB 涨到约 2.5GB** —— 这本身就在把机器写到饱和，是 A 类的触发源之一。
已加编译期 `-Dlite=true`：官方对比跳过这四组（单轮 ~1.0GB），重型探针单独批次跑。

**修法：改成 ABBA 交替采样**（`tools/run-abba.ps1`）。同一轮内每个引擎各跑两次、分处前后半段，
坏窗口必然命中双方；判定用「每引擎两样本取中位 → 再算配对比值」（`tools/abba-verdict.ps1`）。

## 四、P2 已知局限（不修，但必须记录）

### 4.1 `wal_rotate_recreate` 分支的重建失败

```zig
self.wal.close();                                   // self.wal 变 undefined
self.dir.deleteFile(...) catch {};
self.wal = try walmod.Wal.create(...);              // 失败 → self.wal 仍是 undefined
```

后续任何 `put` 都会在 undefined 上做 IO。**这是旧路径就有的问题**（原代码结构相同），
新路径（`reset`）反而更安全（`self.wal` 始终有效）。

不修的理由：该分支**仅用于基准 A/B**，生产恒 `false`；修它需要引入「句柄状态机」，
对产品零收益。若将来要把「重建」变成产品能力，必须先修这条。

### 4.2 `Wal.reset` / `maybeAutoCompact` 的失败路径无用例

两处都需要 mock IO 才能构造失败。列为长期缺口。
