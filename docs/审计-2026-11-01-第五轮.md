## 二、逐项审计

### 2.1 `MergeIter` 堆化 —— 通过

| 检查点 | 结论 |
|---|---|
| 堆内比较用 `refLess`（含「同 key 时 seq 大的在前」） | ✅ 第一版只比 key，被 3 个既有用例当场抓住，已修 |
| `heap_len == 0` 时返回 null | ✅ `next()` 首行即判 |
| 某个游标先耗尽 | ✅ `heap_len -= 1` 后把堆尾挪到根再 siftDown |
| `init` 中途分配失败 | ✅ `errdefer self.deinit()`；`heap` 失败时仍是 `&.{}`，不会误 free |
| 单游标路径（k=1）不建堆 | ✅ 保留线性去重，更快 |
| 2 路归并走堆是否比线性慢 | ⚠️ **未测**（P3，见遗留项） |

### 2.2 段裁剪 —— 通过（并补了可观测性）

- 只剪「段在查询之后」：用稀疏索引第 0 条（= 段内最小 key）判 `>= end`（`end` 排他）。**不改磁盘格式**。
- 「段在查询之前」剪不掉：需要段的**最大** key，稀疏索引给不出精确值（最后 ≤STRIDE-1 行没有索引项）—— 这一点在代码注释里写明了。
- **审计发现：只看结果永远看不出裁剪有没有生效**（不剪只是慢、结果一样）。
  → 新增 `Table.merge_cursors_built`（最近一次 init 实际建了几个游标），并让用例断言它。
  **有效性已验证**：撤掉裁剪后用例立刻报「期望建 3 个游标，实际 5 个」。

### 2.3 Bloom 在线累积 —— 通过

- `bits_len = max(64, expected_rows * bloom_bits)`，写进索引头，读取侧按同一值取模 ⇒ 自洽。
- 实际行数超预估：只抬高误报率，**不产生假阴性**（有用例；注入「少置一位」的缺陷后用例立刻抓到）。
- `bloom_bits == 0` 不分配位图、`bits_len` 写 0（有用例反向覆盖）。
- `hashPair` 未重复计算（`push` 里不再单独调用）。

### 2.4 `forEachRow` —— 通过

- 与 `selectRows` 语义一致：9 个 case（全表 / where / limit / offset / 投影 / 排序 / PK 等值 / limit 0）逐行逐列对拍。
- **回调参数只在回调期间有效**这条约束真实存在：一致性用例第一版只存 `sql.Value` 数组，
  物化回退路径一 `deinit` 就段错误。
- `limit == 0` → 首次循环即 break ✅；`offset` 与 `limit` 的先后判断正确 ✅。

### 2.5 `decodeAll` 改 value 切片 —— 通过

全部 2 个调用点已更新（`selectByPk` 传 `[1][]const u8`、`selectRows` 传 `src`）。

## 三、发现的问题

### P1（已修）`keep.ensureTotalCapacity(alloc, cap)` 按全表上界预分配

`cap` 是「各段行数 + memtable 行数」的上界，而 **WHERE 的选择性事先完全未知**：
200 万行的表跑一个只命中几行的条件，会预先申请 32 MB。

**修法**：WHERE 分支给 4096 的初值，命中多时按 ArrayList 的 2× 自然增长；
无 WHERE 分支保留预分配但封顶 100 万条（16 MB），因为该分支的 cap 接近实际行数。

**⚠️ 必须如实说明**：A/B 实测（新增 `sql_where_rare` 基准，200 万行表 + 命中 0 行的条件）

| | `sql_where_rare` |
|---|---|
| 修复后（初值 4096） | 72,988,172 行/s |
| 撤掉修复（全表上界） | 71,275,075 行/s |

**只差 2.3%**。原因是 `smp_allocator` 对大块分配走 `mmap` 且**惰性提交**：
只申请不写就没有缺页，几乎零成本。

所以这条的定性是 **「多余的虚拟内存预留」**，**不是性能缺陷** ——
它的价值在「32 位地址空间 / 容器内存限额」这类环境，不在吞吐。**不能记成性能优化。**

### P2（已补用例）堆化与段裁剪缺少直接用例

原有覆盖只有 `compact` / `scanRefs` 的间接用例。已补两个：

1. `MergeIter 堆化：多段 key 交错时顺序正确，且部分游标先耗尽不影响结果`
   —— seg0{0,3,6} / seg1{1,4,7,9} / seg2{2,5,8}，断言输出严格 0..9 且无重无漏。
2. `MergeIter 段裁剪：查询只落在一段内时结果与全量过滤一致`
   —— 5 段不重叠 + 5 种区间（段内 / 跨段 / 全区间 / 空区间 / 数据之后），
   同时断言**结果正确**与**建了几个游标**。

### P2（记录，未改）WHERE 分支用 `decodeRowInto` 解码全列

`SELECT id FROM t WHERE v = ...` 会解码所有列才能判断谓词。惰性列解码是 §16.1.10
已记的后续项，涉及 `decodeRowInto` 的跳列实现（变长列仍需读 varint），本轮不做。
