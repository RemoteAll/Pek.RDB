- **M0 关键坑（实测暴露）**：`open` 不能把追加点设在「最后一条合法记录末尾」——掉电撕裂时那几个字节已编程过，NOR 只能 1→0，再写会 DeviceFailure。必须把追加点跳到**下一扇区边界**并在扇区尾写 0x00 标记。撕裂尾用例是这条的唯一守门人。

- **M0 压缩 / 环形日志（2026-10-31 已实现）**：分区为环形追加日志（新增 `tail_at[]` 存活区起点，`rawAppend` 尾部放不下就回卷）；`compact(p, scratch≥2扇区)` 按环序搬「后面无同 key 更新」的记录再擦旧扇区；`hasNewer` 用环序距离判定；`get` 按「距 tail 距离」取最新；`scanPartition` 不再遇空扇区 break。实测代价：riscv32 flash 1,610→**1,976B**、thumb 1,370→**1,810B**、TinyStore 32→**40B**、引擎 RAM 88→**96B**。
- **M0 环形日志三个真 bug（都被用例打出来）**：①回卷只判 `slot<tail` 不够，`tail==start` 时回卷覆盖活数据 → 必须 `slot+len<=tail`；②跨扇区无条件写 `at-1=0` 会踩上一条记录 → 仅当 `append%ssize!=0` 才写；③空分区首条写入后未更新 `tail` → 回卷判定失效。**写满/回卷/掉电重开三类用例是这块的唯一守门人。**

- **物化路径先量成本再砍（2026-11-01，决策记录四十四；用户原话「物化 vs 只推进游标 11,054,915 / 11,754,694 0.94×（非对等）这个还是低了啊」）**：**§16.1.9 按分配量推算的成本模型错了 7 倍**（猜 buf 3.2+flat 3.2+hdrs 1.6+decode 4.7=12.7ms，实测 89ms）。加 `mat_*` 分段基准后真相：**瓶颈是收集参考数组 59ms（66%），不是解码 13ms**。两刀：①**预分配容量**（`scanRefs` 从空 append 到 100 万条经约 20 次扩容、累计复制近百 MB → 用「各段行数 + memtable 行数」上界 `ensureTotalCapacity`）单独就把 `sql_full` 11.29M → 17.00M；②**只收 value 不收 key**（新增 `Table.scanValues()`：`RefRecord` 48 字节 = key16+seq8+flags1+padding+value16，该路径只用 value 16 字节，输出 48MB→16MB；`scanRefs` 59ms→`scanValues` 32–34ms；顺带 WHERE 分支改流式过滤不再收中间数组）。**实测（同批次三轮）`sql_full` 11,054,915 → 18,757,362（+69.7%，区间 17.20–19.35M）**；**vs SQLite 只推进游标 11,754,694 = 0.94× → 1.60×（最不利 1.38×，区间不重叠）；vs SQLite 取两列值 9,288,484 = 2.02×**；`sql_each` 37,201,551 基本不变。**教训：按分配量推算耗时不可靠，必须分段实测**（偏差 7 倍，照那个模型会去优化 decode 而放过收集）。**剩余 56ms 拆解**：scanValues 32–34 + buf 复制 10–11 + decode 12–13 + hdrs 2；**下一步合并「收集」与「复制」为一次遍历**（现在扫两遍），估计 56→~36ms，难点是 `buf` 须遍历前定大小（段文件大小之和是安全上界，memtable 部分要单独处理）。**向量化评估（用户问「当前这个是不是也可以支持向量化引擎」）**：当前瓶颈不在向量化能解决的地方——解码只占 22%（快 2× 也只省 6ms），向量化主场是表达式求值/聚合/过滤下推而我们**还没有表达式树**，真正瓶颈「收集+复制」78% 是内存分配拷贝问题；等 M2 有表达式与聚合、出现「按列批量计算」负载再评估。
- **借鉴 SQLite：结果集不该物化（2026-11-01，决策记录四十三；用户原话「sqlite 是不是开源的，是不是可以分析借鉴下开源源码，我记得也有不少项目也是对标和参考 sqlite，难道就没有性能超越的可以借鉴参考么」）**：**SQLite 是 Public Domain**，可读可抄可商用；特定负载超它的有 DuckDB（向量化/列存/ART）、LMDB（mmap COW B+tree）、TigerBeetle（LSM）、ClickHouse，**但没人能在「嵌入式+OLTP+通用 SQL」主场全面超过它**，能借鉴的是做事方式。**SQLite 的方式=不构造结果集**：`sqlite3_step` 走 VDBE 单步，游标一步一行，列值写进 `pMem` 数组（prepare 时按列数分配）**每步覆写不累积**，`OP_Column` 还**惰性**（不调 `sqlite3_column_*` 就解码）。PostgreSQL `TupleTableSlot`、DuckDB chunk 同理。**我们错在两个维度都不对等**：`selectRows` 全列解码 + 物化完整 `Rows`（100 万×2 列 = flat 48MB + buf 32MB + hdrs 16MB = **96MB**，数据只有 32MB），而 SQLite 基准只数行不解码。**新增 `exec.forEachRow(t,s,sel,alloc,ctx,cb)`**：游标逐行解码到**复用 scratch**、回调消费；无 ORDER BY 且非 PK 等值时流式，有排序/PK 等值时回退物化；语义与 `selectRows` 完全一致（用例 9 个 case 逐行逐列对拍）。**回调参数只在回调期间有效**（text/blob 指向段 mmap）—— 这条不是理论风险：一致性用例第一版只存 `sql.Value` 数组，物化回退路径一 `deinit` 就段错误。SQLite 侧补 `sql_full_touch`（`get::<i64>(0)` + `get_ref(1)`，都不 malloc）才是同口径。**实测（同批次三轮，区间不重叠）**：流式+解码两列 **34,089,088**（30.20–37.64M）vs SQLite 9,288,484（8.06–9.31M）= **3.67×**；物化+解码两列 11,054,915 vs 9,288,484 = 1.19×（最不利 1.15×）；物化 vs SQLite 只推进游标 11,754,694 = 0.94×（不是对等比较）。我们流式比自己物化快 **3.08×**；`sql_each_readrows` 恒 1,000,000（读了全表）。**教训**：①**跨批次比较是陷阱**（SQLite 自身 12.45M→11.68M 波动 6%，跨批次能得出相反结论，比值必须同批次算）；②**比性能先比「做的工作是否相同」**；③**API 形态决定上限**（`selectRows` 返回完整 Rows 就必然物化，只能加流式 API 根治）；④**自己写的警告自己第一个踩到**。还能借鉴：惰性列解码（`SELECT id FROM t` 只解 1 列，变长列仍需读 varint 跳过）、ART 索引（M2）、向量化、编译执行（还没表达式树）。
- **SQL 层全表扫描优化（2026-11-01，决策记录四十二；用户原话「**SQL 层全表扫描我们确实慢 ~23%** 要看怎么提升」）**：**先纠口径**——之前拿「1 万行区间裸扫描 10.5M」比「100 万行 SQL 全表 9.5M」是错的。补同口径（100 万行）基线：`scan_refs_full1m` 16.72M / `scan_full1m` 12.50M / `sql_full` 10.79M / SQLite `SELECT *` 12.45M → **裸扫描与 SQLite 基本持平（1.00×），存储层不落后**，损耗全在 exec 层（裸→SQL 掉 13.7%）。**找到两处纯复制**：①无 WHERE 时 `keep.appendSlice(refs.items)` 复制 48MB → 改 `src = refs.items` 直接引用；②`buildOutput` 恒等投影 `@memcpy(out_rows, m.hdrs)` 复制 16MB → **全量（start==0 && end==hdrs.len）时把 `m.hdrs` 所有权直接转给 `Rows`**（必须判 start/end，因为部分切片长度与分配长度不同而 `Rows.deinit` 按 len 调 free）。**实测 +13.2%**（9.54M→10.79M，两期区间不重叠确定），**0.77× → 0.87×，差距 23%→13%**。剩下 13% 按分配量拆：buf 32MB memcpy 3.2ms + flat 32MB 3.2ms + hdrs 16MB 1.6ms + decode 100 万次 4.7ms——**都是「物化」固有成本**（我们 `selectRows` 返回完整 Rows，SQLite 是 `while rows.next()` 不物化）。根治只能靠 **M2 的流式 API**；`Rows.buf` 零拷贝指向 mmap 会因 compaction 悬垂，**不做**。**坑**：`out_rows` 原本在最前面分配，全量转移路径 return 会漏掉 → 分配必须挪到那条路径之后。新增诊断基准 `scan_full1m` / `scan_refs_full1m`（各分配 98MB/48MB，放 t 生命周期末尾）。

- **「不可区分」的解释 + 范围扫描定案 3.94×（2026-11-01，决策记录四十八，架构 §16.1.14；用户原话「范围扫描 ×2、SQL 插入、超内存写、超内存冷重开区间重叠 → 不可区分 这个是啥意思，是否还有其他可以推进调优的」）**：**「不可区分」≠「打平」，是「这组数据不足以证明谁快」**——判据看三轮 min–max 区间：不重叠（我们最慢仍快过 SQLite 最快）才能下结论；重叠则无法排除「SQLite 这轮恰好偏慢」，必须加大样本或换口径。**范围扫描两档之前不可区分，根因是样本只 1 万行**（绝对耗时 <1µs，测的是 Windows 100ns 计时粒度）。放大到 20 万行后含值档分开（1.85×，区间 12.17–12.96M vs 5.90–7.42M），**仅 key 档仍重叠 —— 老毛病第 4 次复发：我们 `scan_refs_full` 收集 20 万条 RefRecord（写 9.6MB），SQLite `scan_big` 只推进游标一条不收集**。**补对等档（两边都只数行、不收集不解码）**：内存表 `count_range` ↔ SQLite `scan_big`、超内存表 `big_count_range` ↔ SQLite `big_count_range`。**结果翻案**：范围扫描（仅 key 20 万行）**55,521,626（52.26–59.80M）vs 14,098,307（12.85–15.91M）= 3.94×**；超内存同口径 **45,151,823（36.25–45.72M）vs 15,491,627（10.52–15.59M）= 2.91×**；同批顺带洗清**超内存写 1.00×→1.99×**（1.12–1.30M vs 0.28–0.90M 不重叠）、超内存全表遍历 2.37×→3.03×。**代价拆解（同区间三档只差做多少事）**：`count_range` 只推进游标 55.5M(100%) → `scan_refs_full` +收集 9.6MB 17.8M(32%) → `scan_full` +解码全列 12.3M(22%) ⇒ **最大单点开销是「收集」不是「解码」**（收集掉 3.1×、解码再掉 1.45×），继续提速应先做**流式输出**（`forEachRow` 已有，范围扫描入口还没接）而不是惰性列解码。**本轮唯一区间不重叠的落后项：超内存冷重开 2.22ms vs 1.79ms（慢 24%，绝对差 0.43ms）**，需拆解 recover 内部（开段/读 index.bin/解析/建 Bloom）。**工程坑（差点被骗）**：`zig build` 默认 **Debug**，会把 `-Doptimize=ReleaseFast` 产物覆盖 → 整机慢 4–5×（`put` 1.65M→0.31M），**发现「所有指标同步变慢」先查构建模式，别查代码**；跑基准前必须确认 BUILD=0 且 ReleaseFast。新增基准档：Zig `count_range`/`big_count_range`，SQLite `big_count_range`；`compare-bench.ps1` 映射表已改为对等口径、旧不对等档标注「留档不计入结论」。剩余可推进项（有实测支撑，按性价比）：①超内存冷重开 +24%；②收集开销（3.1×，流式出口）；③归并 1.35×（需段记录 max_key，改索引格式升 format）；④惰性列解码（排在收集之后）；⑤2 路归并堆 vs 线性未实测；⑥SQL 插入 1.14× 仍重叠需更大样本；⑦多线程并行扫描（唯一能突破单线程访存带宽的路）。
- **照 SQLite 做：索引 mmap + 懒解析，冷重开 2.06 → 0.67ms（2026-11-01，决策记录五十，架构 §16.1.16；用户原话「如果还是慢的话，那你不能直接分析sqlite的开源代码来同样处理么？」）**：**先纠正前提**——同口径下我们本来就不慢（2.06 vs SQLite 2.40ms，区间重叠），但用户问到真问题：**SQLite 凭什么便宜**。查源码：`sqlite3BtreeOpen` **只保留 `pPage1`（数据库文件第 1 页）**，schema/索引页/叶页全部按需缺页，连 `sqlite_master` 都到第一次 prepare 才读 ⇒ **它的 open ≈ 打开文件 + 读一页**；我们反过来，open 时把 3.13MB `seg/index.bin` 整个读进堆+逐段解析+CRC（§16.1.15 实测 `idx_copy` 1.11ms + `idx_alloc` 0.25ms）。**不是实现差，是调用时机跟它相反**。**可行性先验证**：索引格式 `magic + rows/min_seq/max_seq/n + entries + bloom + CRC(尾)`，元信息都在开头 40B、段裁剪只要第 1 条稀疏索引 ⇒ 只读头部够用；唯一风险是 `compact()` 的「写 tmp + rename 覆盖」在归档被 mmap 时是否被拒 → **写用例 `test "mmap 存活时 rename 覆盖同路径"` 实测成功**（Zig 打开文件带 FILE_SHARE_DELETE，映射继续指向旧 inode）→ **58/58 通过，方案成立**。**改法**：①归档改 mmap（`segmod.IndexMap` + `mapWholeFile`）；②`parseIdxBytes` 拆 `parseIdxHeader`（open，≈40B/段）与 `parseIdxBody`（首次使用，CRC+entries+Bloom）；③`ensureParsed()` 挂 `get`/`scanRefs`/`cursor`/`scanRange` 四个入口，`entryKey` 加 `assert(parsed)`；④段裁剪改用 `firstKey()`；⑤**CRC 变懒校验**（翻位错误从 open 推迟到首次使用，守门用例改为「open 成功但 ensureParsed 报 BadIndexChecksum」）。**实测（同批三轮，区间不重叠）**：超内存冷重开 **2.06 → 0.67ms（3.1×）**，vs SQLite 1.91ms = **快 2.9×，区间不重叠**；**冷重开 1M 0.57ms vs SQLite 2.64ms = 快 4.6×**；`idx_copy` 1.11→**0**、`idx_alloc` 0.25→0、`segs` 0.35→**0.05**。**「重开+查询」没变慢**（`big_get_after_reopen` 601,460→602,146，10 万次点查把解析摊到 0.6%）；**其余指标零退化**（count_range 55.5→54.8M、sql_full 17.3→18.8M、sql_each 34.4→36.0M、big_count 40.2→39.0M）。**新瓶颈：WAL 两次打开 0.39ms（58%）**——同一 wal 被 `replay` 与 `openAppend` 各开一次，列下一轮。**教训（推翻自己第 49 节）**：§16.1.15 判定「不做懒加载」错在**只看单点指标**——「该不该做」之前还有一步：**别人为什么不做这件事**。**照抄 SQLite 的正确形态不是抄代码，是抄调用时机：能用少量元信息做完的事，不要 open 时做全量**；懒解析不省成本，而是把成本搬到真正用到的那一刻（多数场景不会发生在所有段上）。

- **WAL 两次打开合并：确定性省一次 syscall，整机不可区分（2026-11-01，决策记录五十一，架构 §16.1.17）**：§16.1.16 后冷重开只剩 0.67ms，分项 `wal_replay` 0.24 + `wal_open` 0.15 = **0.39ms（58%）** 成最大项——同一 `wal/000001.wal` 被 `replay()`（openFile+stat+read）与 `Wal.openAppend()`（createFile+stat）**各开一次**。**改法**：新增 `walmod.openReplay()` 一次 `createFile(.read=true,.truncate=false)` 同时拿「旧内容」与「追加句柄」；顺手把两份逐字重复的批次解析抽成 `parseBatch`/`parseBatches`/`freeBatches`（`replay` 原 `errdefer batches.deinit(alloc)` 只释放数组不释放 `ops`，是既有泄漏点，一并修掉）。**实测**：`wal_open` 0.15 → **0.00（恒为 0，确定事实）**，`wal_replay`（现含 open）0.39 → 中位 0.25 —— **该段确实省 ~0.15ms**；但整机 `big_recover` 前 0.62/0.67/1.38（中位 0.67）vs 后 0.61/0.80/0.89/0.99/1.85（中位 0.89），**区间重叠 → 不可区分**（Windows 文件系统+杀毒抖动 ±0.5ms 远大于 0.15ms）。**冷重开线收工**：2.06 → 0.67ms（3.1×），对 SQLite 2.9–4.6×；剩余 `dirs` 里约 0.30ms 是 `MemoryMap.create`（CreateFileMapping+MapViewOfFile）的**平台成本**，换写法也得付，继续压只有「索引与数据合并成单文件映射」这类收益 <0.3ms 的结构改动，不值得。**教训：优化到「只剩平台成本」就该停手，别为继续出数字去改架构。**

- **收集开销：scanRange 两遍化 +58%，同款改法用在 decodeAll 是 -31%（2026-11-01，决策记录五十二，架构 §16.1.18）**：§16.1.14 拆出「收集占 3.1×」（`count_range` 55.5M 只推进游标 → `scan_refs_full` 17.8M +收集 20 万条 48B → `scan_full` 12.3M +解码）。**改动（保留）**：`Table.scanRange` 原为「scanRefs 收集全部 refs（9.6MB）→ 算总字节 → 分配 buf → 逐条复制」，那 9.6MB 只为「知道 buf 多大」而付；改成**两遍遍历**（第一遍只统计条数与总字节，第二遍边遍历边填），`RecordSet` 结构不变。**实测 `scan_full` 11,504,567 → 18,208,137（+58%）、`scan_full1m` 10,865,125 → 18,428,220（+70%）**，对 SQLite 比值 2.02× → **2.69×**（区间不重叠）。**同款改法用在 `decodeAll`（SELECT 无 WHERE 主路径）是负优化，已回退**：加了 `decodeAllRange()` 两遍遍历，**实测 `sql_full` 18.63M → 12.86M（-31%）**，函数删除并在原地留注释记实测数字。**不对称的原因**：scanRange 省的是 48B/条 × 20 万（ArrayList 扩容复制贵）、多付 20 万行归并 3.6ms；decodeAllRange 省的是 16B/条 × 100 万（连续写便宜）、多付 100 万行 25 段归并 ~25ms。**教训：「省掉中间数组」不是无条件优化**——判据是「省下的写入（元素大小×条数）」vs「多付的遍历（行数×段数）」，**同一个句式在不同规模下结论相反，只能逐项实测不能类推**。工程细节：Zig 文档注释 `///` 不能用于语句位置（局部变量前会报 `expected statement, found 'a document comment'`）；替换代码块时容易漏掉相邻的 `defer xxx.deinit()`，内存泄漏测试（SafeAllocator）会立刻抓到。本批 `超内存写` 0.09×、`逐行写` 5.08× 属机器负载异常（96K–1.05M，波动 10 倍），不作回归依据。
