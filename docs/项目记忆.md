- **M0 关键坑（实测暴露）**：`open` 不能把追加点设在「最后一条合法记录末尾」——掉电撕裂时那几个字节已编程过，NOR 只能 1→0，再写会 DeviceFailure。必须把追加点跳到**下一扇区边界**并在扇区尾写 0x00 标记。撕裂尾用例是这条的唯一守门人。

- **M0 压缩 / 环形日志（2026-10-31 已实现）**：分区为环形追加日志（新增 `tail_at[]` 存活区起点，`rawAppend` 尾部放不下就回卷）；`compact(p, scratch≥2扇区)` 按环序搬「后面无同 key 更新」的记录再擦旧扇区；`hasNewer` 用环序距离判定；`get` 按「距 tail 距离」取最新；`scanPartition` 不再遇空扇区 break。实测代价：riscv32 flash 1,610→**1,976B**、thumb 1,370→**1,810B**、TinyStore 32→**40B**、引擎 RAM 88→**96B**。
- **M0 环形日志三个真 bug（都被用例打出来）**：①回卷只判 `slot<tail` 不够，`tail==start` 时回卷覆盖活数据 → 必须 `slot+len<=tail`；②跨扇区无条件写 `at-1=0` 会踩上一条记录 → 仅当 `append%ssize!=0` 才写；③空分区首条写入后未更新 `tail` → 回卷判定失效。**写满/回卷/掉电重开三类用例是这块的唯一守门人。**

- **物化路径先量成本再砍（2026-11-01，决策记录四十四；用户原话「物化 vs 只推进游标 11,054,915 / 11,754,694 0.94×（非对等）这个还是低了啊」）**：**§16.1.9 按分配量推算的成本模型错了 7 倍**（猜 buf 3.2+flat 3.2+hdrs 1.6+decode 4.7=12.7ms，实测 89ms）。加 `mat_*` 分段基准后真相：**瓶颈是收集参考数组 59ms（66%），不是解码 13ms**。两刀：①**预分配容量**（`scanRefs` 从空 append 到 100 万条经约 20 次扩容、累计复制近百 MB → 用「各段行数 + memtable 行数」上界 `ensureTotalCapacity`）单独就把 `sql_full` 11.29M → 17.00M；②**只收 value 不收 key**（新增 `Table.scanValues()`：`RefRecord` 48 字节 = key16+seq8+flags1+padding+value16，该路径只用 value 16 字节，输出 48MB→16MB；`scanRefs` 59ms→`scanValues` 32–34ms；顺带 WHERE 分支改流式过滤不再收中间数组）。**实测（同批次三轮）`sql_full` 11,054,915 → 18,757,362（+69.7%，区间 17.20–19.35M）**；**vs SQLite 只推进游标 11,754,694 = 0.94× → 1.60×（最不利 1.38×，区间不重叠）；vs SQLite 取两列值 9,288,484 = 2.02×**；`sql_each` 37,201,551 基本不变。**教训：按分配量推算耗时不可靠，必须分段实测**（偏差 7 倍，照那个模型会去优化 decode 而放过收集）。**剩余 56ms 拆解**：scanValues 32–34 + buf 复制 10–11 + decode 12–13 + hdrs 2；**下一步合并「收集」与「复制」为一次遍历**（现在扫两遍），估计 56→~36ms，难点是 `buf` 须遍历前定大小（段文件大小之和是安全上界，memtable 部分要单独处理）。**向量化评估（用户问「当前这个是不是也可以支持向量化引擎」）**：当前瓶颈不在向量化能解决的地方——解码只占 22%（快 2× 也只省 6ms），向量化主场是表达式求值/聚合/过滤下推而我们**还没有表达式树**，真正瓶颈「收集+复制」78% 是内存分配拷贝问题；等 M2 有表达式与聚合、出现「按列批量计算」负载再评估。
- **借鉴 SQLite：结果集不该物化（2026-11-01，决策记录四十三；用户原话「sqlite 是不是开源的，是不是可以分析借鉴下开源源码，我记得也有不少项目也是对标和参考 sqlite，难道就没有性能超越的可以借鉴参考么」）**：**SQLite 是 Public Domain**，可读可抄可商用；特定负载超它的有 DuckDB（向量化/列存/ART）、LMDB（mmap COW B+tree）、TigerBeetle（LSM）、ClickHouse，**但没人能在「嵌入式+OLTP+通用 SQL」主场全面超过它**，能借鉴的是做事方式。**SQLite 的方式=不构造结果集**：`sqlite3_step` 走 VDBE 单步，游标一步一行，列值写进 `pMem` 数组（prepare 时按列数分配）**每步覆写不累积**，`OP_Column` 还**惰性**（不调 `sqlite3_column_*` 就解码）。PostgreSQL `TupleTableSlot`、DuckDB chunk 同理。**我们错在两个维度都不对等**：`selectRows` 全列解码 + 物化完整 `Rows`（100 万×2 列 = flat 48MB + buf 32MB + hdrs 16MB = **96MB**，数据只有 32MB），而 SQLite 基准只数行不解码。**新增 `exec.forEachRow(t,s,sel,alloc,ctx,cb)`**：游标逐行解码到**复用 scratch**、回调消费；无 ORDER BY 且非 PK 等值时流式，有排序/PK 等值时回退物化；语义与 `selectRows` 完全一致（用例 9 个 case 逐行逐列对拍）。**回调参数只在回调期间有效**（text/blob 指向段 mmap）—— 这条不是理论风险：一致性用例第一版只存 `sql.Value` 数组，物化回退路径一 `deinit` 就段错误。SQLite 侧补 `sql_full_touch`（`get::<i64>(0)` + `get_ref(1)`，都不 malloc）才是同口径。**实测（同批次三轮，区间不重叠）**：流式+解码两列 **34,089,088**（30.20–37.64M）vs SQLite 9,288,484（8.06–9.31M）= **3.67×**；物化+解码两列 11,054,915 vs 9,288,484 = 1.19×（最不利 1.15×）；物化 vs SQLite 只推进游标 11,754,694 = 0.94×（不是对等比较）。我们流式比自己物化快 **3.08×**；`sql_each_readrows` 恒 1,000,000（读了全表）。**教训**：①**跨批次比较是陷阱**（SQLite 自身 12.45M→11.68M 波动 6%，跨批次能得出相反结论，比值必须同批次算）；②**比性能先比「做的工作是否相同」**；③**API 形态决定上限**（`selectRows` 返回完整 Rows 就必然物化，只能加流式 API 根治）；④**自己写的警告自己第一个踩到**。还能借鉴：惰性列解码（`SELECT id FROM t` 只解 1 列，变长列仍需读 varint 跳过）、ART 索引（M2）、向量化、编译执行（还没表达式树）。
- **SQL 层全表扫描优化（2026-11-01，决策记录四十二；用户原话「**SQL 层全表扫描我们确实慢 ~23%** 要看怎么提升」）**：**先纠口径**——之前拿「1 万行区间裸扫描 10.5M」比「100 万行 SQL 全表 9.5M」是错的。补同口径（100 万行）基线：`scan_refs_full1m` 16.72M / `scan_full1m` 12.50M / `sql_full` 10.79M / SQLite `SELECT *` 12.45M → **裸扫描与 SQLite 基本持平（1.00×），存储层不落后**，损耗全在 exec 层（裸→SQL 掉 13.7%）。**找到两处纯复制**：①无 WHERE 时 `keep.appendSlice(refs.items)` 复制 48MB → 改 `src = refs.items` 直接引用；②`buildOutput` 恒等投影 `@memcpy(out_rows, m.hdrs)` 复制 16MB → **全量（start==0 && end==hdrs.len）时把 `m.hdrs` 所有权直接转给 `Rows`**（必须判 start/end，因为部分切片长度与分配长度不同而 `Rows.deinit` 按 len 调 free）。**实测 +13.2%**（9.54M→10.79M，两期区间不重叠确定），**0.77× → 0.87×，差距 23%→13%**。剩下 13% 按分配量拆：buf 32MB memcpy 3.2ms + flat 32MB 3.2ms + hdrs 16MB 1.6ms + decode 100 万次 4.7ms——**都是「物化」固有成本**（我们 `selectRows` 返回完整 Rows，SQLite 是 `while rows.next()` 不物化）。根治只能靠 **M2 的流式 API**；`Rows.buf` 零拷贝指向 mmap 会因 compaction 悬垂，**不做**。**坑**：`out_rows` 原本在最前面分配，全量转移路径 return 会漏掉 → 分配必须挪到那条路径之后。新增诊断基准 `scan_full1m` / `scan_refs_full1m`（各分配 98MB/48MB，放 t 生命周期末尾）。

- **「不可区分」的解释 + 范围扫描定案 3.94×（2026-11-01，决策记录四十八，架构 §16.1.14；用户原话「范围扫描 ×2、SQL 插入、超内存写、超内存冷重开区间重叠 → 不可区分 这个是啥意思，是否还有其他可以推进调优的」）**：**「不可区分」≠「打平」，是「这组数据不足以证明谁快」**——判据看三轮 min–max 区间：不重叠（我们最慢仍快过 SQLite 最快）才能下结论；重叠则无法排除「SQLite 这轮恰好偏慢」，必须加大样本或换口径。**范围扫描两档之前不可区分，根因是样本只 1 万行**（绝对耗时 <1µs，测的是 Windows 100ns 计时粒度）。放大到 20 万行后含值档分开（1.85×，区间 12.17–12.96M vs 5.90–7.42M），**仅 key 档仍重叠 —— 老毛病第 4 次复发：我们 `scan_refs_full` 收集 20 万条 RefRecord（写 9.6MB），SQLite `scan_big` 只推进游标一条不收集**。**补对等档（两边都只数行、不收集不解码）**：内存表 `count_range` ↔ SQLite `scan_big`、超内存表 `big_count_range` ↔ SQLite `big_count_range`。**结果翻案**：范围扫描（仅 key 20 万行）**55,521,626（52.26–59.80M）vs 14,098,307（12.85–15.91M）= 3.94×**；超内存同口径 **45,151,823（36.25–45.72M）vs 15,491,627（10.52–15.59M）= 2.91×**；同批顺带洗清**超内存写 1.00×→1.99×**（1.12–1.30M vs 0.28–0.90M 不重叠）、超内存全表遍历 2.37×→3.03×。**代价拆解（同区间三档只差做多少事）**：`count_range` 只推进游标 55.5M(100%) → `scan_refs_full` +收集 9.6MB 17.8M(32%) → `scan_full` +解码全列 12.3M(22%) ⇒ **最大单点开销是「收集」不是「解码」**（收集掉 3.1×、解码再掉 1.45×），继续提速应先做**流式输出**（`forEachRow` 已有，范围扫描入口还没接）而不是惰性列解码。**本轮唯一区间不重叠的落后项：超内存冷重开 2.22ms vs 1.79ms（慢 24%，绝对差 0.43ms）**，需拆解 recover 内部（开段/读 index.bin/解析/建 Bloom）。**工程坑（差点被骗）**：`zig build` 默认 **Debug**，会把 `-Doptimize=ReleaseFast` 产物覆盖 → 整机慢 4–5×（`put` 1.65M→0.31M），**发现「所有指标同步变慢」先查构建模式，别查代码**；跑基准前必须确认 BUILD=0 且 ReleaseFast。新增基准档：Zig `count_range`/`big_count_range`，SQLite `big_count_range`；`compare-bench.ps1` 映射表已改为对等口径、旧不对等档标注「留档不计入结论」。剩余可推进项（有实测支撑，按性价比）：①超内存冷重开 +24%；②收集开销（3.1×，流式出口）；③归并 1.35×（需段记录 max_key，改索引格式升 format）；④惰性列解码（排在收集之后）；⑤2 路归并堆 vs 线性未实测；⑥SQL 插入 1.14× 仍重叠需更大样本；⑦多线程并行扫描（唯一能突破单线程访存带宽的路）。
- **照 SQLite 做：索引 mmap + 懒解析，冷重开 2.06 → 0.67ms（2026-11-01，决策记录五十，架构 §16.1.16；用户原话「如果还是慢的话，那你不能直接分析sqlite的开源代码来同样处理么？」）**：**先纠正前提**——同口径下我们本来就不慢（2.06 vs SQLite 2.40ms，区间重叠），但用户问到真问题：**SQLite 凭什么便宜**。查源码：`sqlite3BtreeOpen` **只保留 `pPage1`（数据库文件第 1 页）**，schema/索引页/叶页全部按需缺页，连 `sqlite_master` 都到第一次 prepare 才读 ⇒ **它的 open ≈ 打开文件 + 读一页**；我们反过来，open 时把 3.13MB `seg/index.bin` 整个读进堆+逐段解析+CRC（§16.1.15 实测 `idx_copy` 1.11ms + `idx_alloc` 0.25ms）。**不是实现差，是调用时机跟它相反**。**可行性先验证**：索引格式 `magic + rows/min_seq/max_seq/n + entries + bloom + CRC(尾)`，元信息都在开头 40B、段裁剪只要第 1 条稀疏索引 ⇒ 只读头部够用；唯一风险是 `compact()` 的「写 tmp + rename 覆盖」在归档被 mmap 时是否被拒 → **写用例 `test "mmap 存活时 rename 覆盖同路径"` 实测成功**（Zig 打开文件带 FILE_SHARE_DELETE，映射继续指向旧 inode）→ **58/58 通过，方案成立**。**改法**：①归档改 mmap（`segmod.IndexMap` + `mapWholeFile`）；②`parseIdxBytes` 拆 `parseIdxHeader`（open，≈40B/段）与 `parseIdxBody`（首次使用，CRC+entries+Bloom）；③`ensureParsed()` 挂 `get`/`scanRefs`/`cursor`/`scanRange` 四个入口，`entryKey` 加 `assert(parsed)`；④段裁剪改用 `firstKey()`；⑤**CRC 变懒校验**（翻位错误从 open 推迟到首次使用，守门用例改为「open 成功但 ensureParsed 报 BadIndexChecksum」）。**实测（同批三轮，区间不重叠）**：超内存冷重开 **2.06 → 0.67ms（3.1×）**，vs SQLite 1.91ms = **快 2.9×，区间不重叠**；**冷重开 1M 0.57ms vs SQLite 2.64ms = 快 4.6×**；`idx_copy` 1.11→**0**、`idx_alloc` 0.25→0、`segs` 0.35→**0.05**。**「重开+查询」没变慢**（`big_get_after_reopen` 601,460→602,146，10 万次点查把解析摊到 0.6%）；**其余指标零退化**（count_range 55.5→54.8M、sql_full 17.3→18.8M、sql_each 34.4→36.0M、big_count 40.2→39.0M）。**新瓶颈：WAL 两次打开 0.39ms（58%）**——同一 wal 被 `replay` 与 `openAppend` 各开一次，列下一轮。**教训（推翻自己第 49 节）**：§16.1.15 判定「不做懒加载」错在**只看单点指标**——「该不该做」之前还有一步：**别人为什么不做这件事**。**照抄 SQLite 的正确形态不是抄代码，是抄调用时机：能用少量元信息做完的事，不要 open 时做全量**；懒解析不省成本，而是把成本搬到真正用到的那一刻（多数场景不会发生在所有段上）。

- **WAL 两次打开合并：确定性省一次 syscall，整机不可区分（2026-11-01，决策记录五十一，架构 §16.1.17）**：§16.1.16 后冷重开只剩 0.67ms，分项 `wal_replay` 0.24 + `wal_open` 0.15 = **0.39ms（58%）** 成最大项——同一 `wal/000001.wal` 被 `replay()`（openFile+stat+read）与 `Wal.openAppend()`（createFile+stat）**各开一次**。**改法**：新增 `walmod.openReplay()` 一次 `createFile(.read=true,.truncate=false)` 同时拿「旧内容」与「追加句柄」；顺手把两份逐字重复的批次解析抽成 `parseBatch`/`parseBatches`/`freeBatches`（`replay` 原 `errdefer batches.deinit(alloc)` 只释放数组不释放 `ops`，是既有泄漏点，一并修掉）。**实测**：`wal_open` 0.15 → **0.00（恒为 0，确定事实）**，`wal_replay`（现含 open）0.39 → 中位 0.25 —— **该段确实省 ~0.15ms**；但整机 `big_recover` 前 0.62/0.67/1.38（中位 0.67）vs 后 0.61/0.80/0.89/0.99/1.85（中位 0.89），**区间重叠 → 不可区分**（Windows 文件系统+杀毒抖动 ±0.5ms 远大于 0.15ms）。**冷重开线收工**：2.06 → 0.67ms（3.1×），对 SQLite 2.9–4.6×；剩余 `dirs` 里约 0.30ms 是 `MemoryMap.create`（CreateFileMapping+MapViewOfFile）的**平台成本**，换写法也得付，继续压只有「索引与数据合并成单文件映射」这类收益 <0.3ms 的结构改动，不值得。**教训：优化到「只剩平台成本」就该停手，别为继续出数字去改架构。**

- **收集开销：scanRange 两遍化 +58%，同款改法用在 decodeAll 是 -31%（2026-11-01，决策记录五十二，架构 §16.1.18）**：§16.1.14 拆出「收集占 3.1×」（`count_range` 55.5M 只推进游标 → `scan_refs_full` 17.8M +收集 20 万条 48B → `scan_full` 12.3M +解码）。**改动（保留）**：`Table.scanRange` 原为「scanRefs 收集全部 refs（9.6MB）→ 算总字节 → 分配 buf → 逐条复制」，那 9.6MB 只为「知道 buf 多大」而付；改成**两遍遍历**（第一遍只统计条数与总字节，第二遍边遍历边填），`RecordSet` 结构不变。**实测 `scan_full` 11,504,567 → 18,208,137（+58%）、`scan_full1m` 10,865,125 → 18,428,220（+70%）**，对 SQLite 比值 2.02× → **2.69×**（区间不重叠）。**同款改法用在 `decodeAll`（SELECT 无 WHERE 主路径）是负优化，已回退**：加了 `decodeAllRange()` 两遍遍历，**实测 `sql_full` 18.63M → 12.86M（-31%）**，函数删除并在原地留注释记实测数字。**不对称的原因**：scanRange 省的是 48B/条 × 20 万（ArrayList 扩容复制贵）、多付 20 万行归并 3.6ms；decodeAllRange 省的是 16B/条 × 100 万（连续写便宜）、多付 100 万行 25 段归并 ~25ms。**教训：「省掉中间数组」不是无条件优化**——判据是「省下的写入（元素大小×条数）」vs「多付的遍历（行数×段数）」，**同一个句式在不同规模下结论相反，只能逐项实测不能类推**。工程细节：Zig 文档注释 `///` 不能用于语句位置（局部变量前会报 `expected statement, found 'a document comment'`）；替换代码块时容易漏掉相邻的 `defer xxx.deinit()`，内存泄漏测试（SafeAllocator）会立刻抓到。本批 `超内存写` 0.09×、`逐行写` 5.08× 属机器负载异常（96K–1.05M，波动 10 倍），不作回归依据。

- **「k 小走线性归并」：没测出结论，但发现基准本身测错了（2026-11-01，决策记录五十三，架构 §16.1.19）**：命题——`MergeIter` 用最小堆做 k 路归并，直觉上 k=2 时线性扫 2 个游标只要 1 次比较、堆要维护 `heap` 间接寻址，所以「游标少时改线性」应该更快；遂加 `merge_linear_max` + `nextLinear()` + `compares` 计数器验证。**三次口径错误全在同一轮内**：①`t5`（刚写完、热）vs `t5h`（新 open）比吞吐 → 「线性快 26%」，实际一边热一边冷（预热后 t5h 1.99M→**42.7M**）；②确认游标数发现 `merge_cursors_multi = 1`——**这一档根本没有 2 路归并**（段范围不重叠，段裁剪剪掉了第 2 段）；③构造重叠两段后比线性 vs 堆 → 「堆快 50%」，**又是冷热**（线性跑第一次、堆跑预热后第二次）。**三次错的是同一件事：A/B 两边状态不一致，而第 1 次刚踩完、第 2 次已发现，第 3 次又踩**。**确定性收获（站得住）**：新增 `MergeIter.compares` / `Table.merge_compares_total`；`merge2_cursors = 2`（重叠两段确实都参与）、`merge2_compares = 399,999` 三轮恒定（= 2×200000−1，k=2 归并不得不做的比较数下界）。**真发现：`scan_refs_multi` / `scan_refs_multi_segs` 一直被当作「2 段归并」性能，实际段裁剪把第 2 段剪掉了——它测的是单游标顺序扫描，2.2–2.5M 行/s 与 k 路归并无关**。**结论：不改动**（产品仍走堆，`nextLinear` 与 `merge_linear_max` 已删），k=2 谁更快如实记「未测出」；保留 compares 计数器与 `merge2` 基准档供后续。**教训**：①**A/B 第一件事是让两边状态一致**，其次才是比较——计时实验里「谁先跑谁吃亏」是系统性偏差不是噪声，不会随轮次平均掉；②**先确认实验真的覆盖了目标代码路径**（否则会拿「单游标」数字下「k 路归并」结论且永远发现不了）；③计数器这类确定性指标是「这一步到底做没做、做了多少」的唯一硬证据。**工程坑**：用 PowerShell 按缩进批量删代码块会误删（`while ($c[$k] -notmatch '^        \}$')` 层级判断错，吞掉了 `concWriter` 函数体），已 `git checkout -- src/main.zig` 恢复——**批量删代码用精确匹配的编辑工具，不要按行号/缩进推算**。

- **第六轮审计：2 个 P1（2026-11-01，决策记录五十四，报告 `docs/审计-2026-11-01-第六轮.md`；用户原话「先前面的做一次审计，没有问题了再往下推进」）**：审 `cc2f424`（mmap+懒解析）、`a468f2f`（WAL 一次打开）、`14a2cfe`（scanRange 两遍化）、`504e3d9`（探针）。**P1-1 `scanRange` 两遍遍历的越界保护依赖 `std.debug.assert`**——它在 ReleaseFast 下被整个抹掉；第二遍若行数变多（并发写让 memtable 变大、违反「扫描期间不得写」）就是**静默堆越界写**（数据损坏级，不崩溃）。改成运行时检查 + `error.ConcurrentModification`，且「变少了」也要报（否则返回 n 条但后半段是未初始化内存）。**P1-2 懒解析破坏了 `compact` 的「先验证再动磁盘」保证**——`compact` 原注释明确「先在内存里建好新段（验证索引可解析）再改磁盘」，但 `fromBytes` 懒解析后只读头部不做 CRC，这步事实上失效，损坏索引也会被当成可用再让 `archiveRewrite` 指向它；修复＝建完新段立即 `ensureParsed()`，**`errdefer` 必须注册在它之前**（否则校验失败时新段 entries 无人释放，因 fromBytes 的 errdefer 管不到调用方这层）。**P2**：①`Replay.deinit` 与 `freeBatches` 两份相同逻辑→复用；②`mayContain`/`candidateIndex` 缺 `assert(parsed)`——前者未解析时返回 true（不丢数据但静默退化成全扫），**后者未解析时二分只在头部那 1 条里找 → 结果直接错**，已补断言。**复核通过**：ensureParsed 覆盖（四入口+三断言）、mmap 生命周期（先 close 段后 destroy）、compact 与 rename 交互、openReplay 资源管理、ensureParsed 幂等、Table.open errdefer 顺序。**遗留不修**：`Segment.open` 单文件模式仍读堆（产品不用）、`mapWholeFile` 空文件当新建库（与原行为一致）、`parseIdxHeader` 无 CRC、`MergeIter.deinit` 依赖 Table 存活、`error.ConcurrentModification` 分支无法用现有 API 触发。**回归**：58 用例全绿、无退化；确定性指标 `merge2_compares` 三轮恒 399,999、`merge2_cursors` 恒 2。**教训：`std.debug.assert` 不是安全检查——ReleaseFast 下它是空的；凡「违反契约会导致越界写/未初始化内存」的路径必须用运行时检查 + 明确错误。**

- **投影查询：先量出「只查一列反而更慢」，再修成 +41%（2026-11-01，决策记录五十五，架构 §16.1.20）**：原计划做「惰性列解码」，**先补了投影基准档**（此前只有 `SELECT *` 档，无法量化投影开销）→ 立刻发现反直觉现象：**物化路径下 `SELECT id`（14,677,499）比 `SELECT *`（17,507,156）慢 16%**；流式下则快 3%。查 `mat_ms` 分段（scanValues 44 + buf_copy 19 + decode 15 + hdrs 2 = 82ms）→ **解码只占 18%，瓶颈不在解码**。真因：`buildOutput` 的部分投影分支另分配 `pflat`（100 万 × 1 = 16MB）并逐行拷 Value，而恒等投影是**直接转移所有权** —— 多付 16MB 分配 + 16MB 写入 ≈ 11ms，正好是那 16%。**修法**：①`schema.decodeRowProjected(dst, want, bytes)` 只解 want 列、其余按类型跳过（text/blob 只读长度 varint 不碰内容）＝真正的 `OP_Column` 惰性；②`decodeAll` 加 `want: ?[]const usize`，`flat` 宽度 = want.len，`Materialized` 加 `ncols`；③`buildOutput` 在 `m.ncols == proj.indices.len` 时走零拷贝转移、不再分配 pflat；④`selectRows` 把 `buildProjection` 提到 `decodeAll` 之前。**两个必须降级的情形**：want 必须严格升序（`SELECT v, id` 给 [1,0]、`SELECT id, id` 给重复下标 → 退回全列，**这条是守门用例当场抓出来的**：forEachRow 与 selectRows 逐行对拍立刻失败）；有 ORDER BY 时（`SortCtx` 用 `schema.indexOf` 拿全列下标）→ 退回全列。**实测（同批三轮）**：`sql_proj1` **14,677,499 → 20,656,249（+41%）**，与 `sql_full` 的关系**从「慢 16% 倒挂」变成「快 8%」**；`sql_full` 19,065,086 噪声内。**教训：优化的方向也可能是错的，而错的只有基准能告诉你**——若没先补投影档，会直接去优化只占 18% 的解码；更糟的是把 flat 改小后因 buildOutput 还在拷 pflat 而毫无变化，然后误判方向。**先量出「反直觉的那一项」，再顺着它找真瓶颈。**

- **归并代价 1.35× 的确定性归因：不是 log k，是每行 2 次比较 + 跨游标调用（2026-11-01，决策记录五十六，架构 §16.1.21）**：同批三轮 25 段中位 **20,814,687** vs 1 段 **28,033,663** = **1.35×**（与 §16.1.13 一致）。**新增 `cm_cursors_*` / `cm_compares_*` 确定性计数器（三轮完全一致）**：25 段 `merge_cursors_built = 25`、比较次数 **1,000,054**（= **2.0 次/行**）；1 段 = 1 游标、**0 次比较**。**关键发现：每行只比较 2.0 次，不是 log₂(25)≈4.6 次**——因为顺序写入的 25 段 key 范围互不重叠，堆顶游标推进后仍是最小值，`siftDown` 第一轮就 `return`（只做 `lessAt(r,l)` + `lessAt(smallest,i)` 两次）。所以 1.35× 的来源是：①每行 2 次 `refLess`（内含 `keyCmp` 逐字节比 key）；②每行一次 `self.cur[bi] = self.cursors.items[bi].next()` **跨游标间接调用**，而单段路径是内联紧循环。**解法（本轮未做，需格式变更）＝顺序拼接**：段范围两两不重叠且有序时按段依次耗尽游标（同时刻只有 1 个活跃）→ 走单游标路径 → **0 次比较**，收益上限即 1.35×（+34%）。**代价**：索引头部加 `u32 klen + max_key`（`PEKZIX02`→`PEKZIX03`、`PEKZAG03`→`PEKZAG04`）；`Writer.finishBytes`/`finish` 加 `max_key` 参数（**由调用方遍历时记最后一个 key，不能每行 dupe——200 万行是 32MB memcpy**）；`MergeIter.init` 加「可拼接」检测 + `nextConcat()`；用例覆盖「不重叠→拼接结果一致」「有重叠（compact 后同 key 新版本）→ 自动退回堆归并」。**适用范围**：只对顺序写入后未 compact 的段有效；compact 后段互相重叠，仍走堆。

- **记录头瘦身 17B→7B：磁盘 −17.1%，与 SQLite 差距 41%→17%（2026-11-01，决策记录六十二，架构 §16.1.26）**：用户原话**「可以动，因为目前还没有正式用上」**（授权改磁盘格式）。**改动**：行格式 `u32 klen|u32 vlen|u64 seq|u8 flags`(17B) → `u8 klen|u8 vlen|u32 seq|u8 flags`(7B)，字段取到定长最大值（255/255/0xFFFFFFFF）时表示「放不下」后跟 varint（**用最大值当逃逸不浪费任何可表示空间，分支几乎永不命中**）；**`IDX_MAGIC` PEKZIX03→PEKZIX04、`ARCHIVE_MAGIC` PEKZAG04→PEKZAG05（破坏兼容）**；顺带把散在 4 处（`Segment.get`/`scanRefs`/`scanRange`/`RefCursor.next`）**完全相同**的解析循环收编成 `codec.readRec`/`codec.writeRecHdr` 一对。**成果**：117,127,373 → **97,127,373 B**（58.56→**48.56 B/行**，−17.1%，三轮逐字节一致），**与理论值 `2M×(7+8+32)+3,127,373` 完全相等**；SQLite 41.56 B/行 → 差距 +41%→**+17%**。**三个坑**：①纯 varint 版本 47 B/行但解码要跑 3 个 varint 循环（seq 占 3 字节）→ 跨批次 big_count 42.9M→38.1M；②**微基准第一版测的是内存带宽不是解码**（100 万条×57B=57MB/趟→13GB/s 顶到带宽，比值 0.76–1.25 乱跳）→ 改 200k 条（11.4/9.4MB）放 L3 + 重复 20 趟；③**真因是 `readRec` 没标 `inline` 且边界检查没被消除**（7B 头第一版配对仍 13/15 对更慢、中位 0.80）→ 改 `pub inline fn` + 「先算剩余再减」写法（`rest = buf.len - p; klen > rest; rest - klen; vlen > after_k`）让编译器证明不越界 → **11/15 对更快、中位 1.065×**。**教训：`inline` 与「可证明的边界检查写法」对小函数的热路径性能影响可达 20%，比算法选择还大。** **本轮流水线数字不能用**：会话后半段机器持续变慢（put 1.66M→1.53M→1.35M、big_count 42.9M→39.0M→35.0M，**连无关的写路径一起掉**）——「所有指标一起变慢先怀疑机器」；只认磁盘字节 + 同进程配对微基准。**还没做**：key 仍定长 8B（块内前缀编码可再省 3–5 B/行，但会牵动 `MergeIter.last_key` 的引用语义）；Bloom 10→8 bit/key。61 用例全绿（新增 `readRec` 往返：空值/254/255/300B key、255B value、seq 跨 2^32、三逃逸同时命中、逐字节截断不 panic、定长头确实 7B）。

- **key 前缀压缩：先量代价，结论暂不做（2026-11-01，决策记录六十三，架构 §16.1.27）**：用户原话**「需要的，如果遇到慢的就和sqlite开源代码中算法对比一下」**。**探针（未改产品代码，同进程配对、L3 常驻 200k 条、重复 20 趟、奇偶轮换）**：7B 定长头 47.00 B/记录（基准）vs 块内前缀压缩 **42.08 B/记录（−10.4%）但解码 0.917×（12/15 对更慢）**；15 对比值 0.813…1.058。且这是**下界**——真实实现还要在 `MergeIter` 里每行多一次整 key 拷贝（key 不再指向稳定内存，现在的 `last_key = rec.key` 零成本引用会失效）。**和 SQLite 开源实现对比（决定性）**：SQLite **不做 key 前缀压缩**——B-tree 页内 key 必须**随机直接寻址**（页内二分查找），delta 编码会让每次比较都得从块首重解；它的 rowid 是 **varint**（3–4 B）且**每次比较都要解 varint**，这正是它点查慢（我们 8.6×）的一部分；它省字节靠「key 更短」+「serial_type 把类型和长度压进一个 varint」，**不是 key 压缩**。**一句话：SQLite 用解码换字节，我们用字节换解码。** 另一条路也不通：把 `encodeI64Key` 改成变长保序编码同样省 4B/行且零拷贝，但会丢掉 `keyCmp` 的 **8 字节 u64 快路径**（`segment.zig` 注释实测占扫描 ~20%）→ 等于用 20% 扫描换 10% 磁盘。**结论：48.56 vs 41.56 B/行（+17%）是用磁盘换速度的结构性选择，不是缺陷。** 什么时候回头：场景变成「磁盘成本 >> 吞吐」（归档/冷数据/边缘），且到时应上**列式块+压缩**（M3），不要做行内前缀压缩。探针留在基准里（`recdec_plain7`/`recdec_pfx`/`recdec_pfx_bytes`），重评估直接重跑。

- **「17% 磁盘」逐项拆解：定长 key 实测值 1.8~4.3 倍（2026-11-01，决策记录六十四，架构 §16.1.28）**：用户原话**「结构性代价那没有更合适的结构和算法能解决这个问题了么？」**。**差距拆解**（48.56 vs 41.56 B/行）：记录头 7 vs 3（+4）、key 8 vs 4（+4）、value 32 vs 32、索引 1.56 vs 0（+1.56）。**关键测量**：所有「省 key 字节」方案都卡在 `keyCmp` 的 u64 快路径上；原注释「逐字节循环占 ~20%」是拿**手写循环**比 u64 且从没量过 memcmp。配对微基准（8192 个 8B key、200 轮、奇偶轮换）中位：**u64 1,200,644,878 次/s（1.00×）｜手写循环 654,548,360（0.545×，慢 1.83×）｜`std.mem.order`/memcmp 279,996,582（0.233×，慢 4.29×）**。→ **定长 8B 不是省 20%，是快 1.8–4.3 倍**；且**顺手证伪「换 std.mem.order 靠 memcmp 向量化变快」的诱惑——它比手写循环还慢 2.3×**（Zig 0.17 该路径没内联成向量比较）。**逐项判定**：key 前缀压缩 −4B（解码 −8.3%，不做）、key 变长保序编码 −4B（比较慢 1.83×，不做）、稀疏索引瘦身 −0.14B（可做）、Bloom 10→8 bit/key −0.25B（可做）、每行 `seq` −4B（MVCC 成本，去掉=放弃快照隔离，**产品决策**）、列式块+压缩（真实数据可达 −50%+，但点查要解块，M3 架构级）。**结论：7B 记录头无一处浪费（klen/vlen 各 1B 已是 varint 下限、seq 是 MVCC、flags 是墓碑）；+17% 磁盘是这套结构的价格，产品是「1.24M 次/s 点查 + 61M 行/s 扫描」；真要压下去唯一正解是改数据布局（列式+压缩），不是继续抠行格式。** 新增 `keycmp_{u64,memcmp,hand}` 配对微基准；产品代码零改动；61 用例全绿。

- **压缩能不能「提高性能」：分场景，且现在测不了（2026-11-01，决策记录六十五，架构 §16.1.29）**：用户原话**「如果真的能解决问题提高性能为什么不做/」**。**①先算是不是带宽受限**：`big_count` 42,867,309 行/s × 47 B = **2.01 GB/s**、超内存范围扫描 1.93 GB/s、内存内范围扫描 **2.88 GB/s**；单线程顺序访存通常 8–15 GB/s → **还有 3–6 倍余量**，说明**不是带宽受限，是指令受限**（每行只读 47 B 却花掉相当于 150–220 B 的时间）。→ **压缩削的是没用满的资源（带宽），加的是真正的瓶颈（指令）；对内存内热数据扫描只会更慢。** **②分场景**：内存内扫描/点查=变慢；**超内存走盘的冷扫描=变快**（IO 带宽 SSD ~1–3 GB/s，少读远大于解压成本）；磁盘成本=省。所以压缩是**冷数据/存储成本优化，不是通用性能优化**。**③关键坑：基准数据是 `const value: [32]u8 = @splat('x')`——每行 32 字节全是 'x'**！对已有磁盘对比**没影响**（48.56 vs 41.56 B/行只由字段宽度决定、与内容无关），但让**任何压缩实验变成假的**（RLE 后 1 字节，能做出「压缩到 1/30」的荒唐结果）；且 `big_*` 只有 94 MB **全在页缓存**、没有 IO 瓶颈，要测冷读得打掉页缓存或做到远超内存，本机不可复现。**→ 在「真实数据形态 + 真冷读」的基准之前，任何压缩结论都不可信。** **结论：现在不做**——它不解决性能（指令受限）、磁盘只多 17%、压缩要付「零拷贝→解块」的结构代价、而且还没测过自己数据的可压缩性。**什么时候做**：出现明确目标场景（冷数据占比高 / 磁盘成本硬约束）时按 M3 列式块设计做，**第一步先补真实数据形态的基准，而不是先写压缩器**。

- **耐久口径对齐：6 项「判不出来」的真因（2026-11-01，决策记录七十，架构 §16.1.31）**：用户原话**「目前就是查不出来有没有落后后sqlite的是吧？」**。**先认错**——上一轮把 6 项未决解释成「机器噪声判不出来」是错的。真因两件：①**口径不对等**：基准表 `wal_sync_every=10_000`（200 万行 **200 次 WAL fsync + 25 次段 fsync**）vs SQLite `synchronous=NORMAL`（WAL 提交**根本不 fsync**，只 checkpoint 刷）→ 自己加两个数量级持久化再比；②**写路径偶发整轮崩塌**（读正常甚至最快、写全线崩 3–6 倍、SQLite 同轮正常）。**已改**：全部基准表切 `wal_sync_every=0`（对等档，**段 flush 仍逐段 fsync，比 NORMAL 还严**），强耐久档另起 `big_put_strong` 参考行。**档位映射（写死，别再各写各的）**：OFF↔`sync=0`+极大 flush_bytes；**NORMAL↔`sync=0`（基准对等档）**；FULL↔`sync=1`；介于↔`sync=N`。**代价实测**：强耐久档 +8~11% 时间，但尾部波动 1.56×→**3.32×**。**结果**：p9 批 7 轮交替配对 `always-ahead=17 / always-behind=0 / unresolved=5`（p7 为 16/0/6）。**剩余 5 项全 6/7，最差比值 0.56–0.72× 全部来自同一轮（p9 r3）**，该轮我方读指标七轮最快、写全线崩、SQLite 正常（我方 sql_put 568K/conc4 666K/big_put 364K vs SQLite 966K/1,179K/505K）。**待办**：7 轮约 1 轮写路径整轮崩塌（已定位未解决），方向＝降文件 churn（合并段 fsync、加大 `flush_bytes`、WAL 复用），**验收用「最小轮次吞吐」而不是中位数**。**新增可观测**：`Table.{ns_wal_sync,ns_flush,flush_calls,ns_flush_max}` + 基准输出 `big_put_breakdown`/`big_put_flushmax`；实测**约 62% 写时间在 fsync**，正常单次 flush 22ms、出问题 203ms（10 倍）。**坑（复发第 2 次，必须记）**：PowerShell `Get-Content -Raw`/`Set-Content` 默认按 ANSI 读 UTF-8，批量改 `.zig` 会**把中文注释整片变成乱码并写入 BOM+CRLF**（本轮发生过，靠 `git checkout` + `[System.IO.File]::ReadAllText(path, UTF8)` / `WriteAllText(..., UTF8Encoding($false))` 修复）。**改源码一律用编辑工具。**

- **写路径崩塌元凶：每次 flush 都在删+建 WAL 文件（2026-11-01，决策记录七十一，架构 §16.1.32）**：用户原话**「请继续」**。根因：`flushImpl` 每次 flush 结束都 `wal.sync → wal.close → deleteFile(wal) → Wal.create(wal)`——**整条写路径上唯一会增删目录项的操作**，200 万行（`flush_bytes=8MB`）重复 25 次。改法：`Wal.reset()` = `setLength(0)` + `sync()` + 复位追加点，**复用同一句柄**（语义等价：memtable 已全部落段，这份 WAL 作废）。`Options.wal_rotate_recreate` 仅供基准 A/B 回退旧路径，生产恒 false。**实测**：同进程配对 A/B（`walab_ratio` = 截断÷重建，7 对）`1.3451|1.9994|1.3532|1.3492|1.3130|2.8131|1.4973` → 7/7 全正、中位 **1.35×**（删+建吃掉写路径约 35%）；`big_put` 中位 1,411,169 → **1,989,890（+41%）**，波动 **4.03× → 1.14×**；`sql_put` 波动 2.53×→1.08×；`conc_put_4t` 5.96×→1.03×。**vs SQLite p10 批 7 轮交替配对：22 项全胜 / 0 落后 / 0 未决**（p9 为 17/0/5），最差比值全部 > 1。无回归：`big_disk_bytes` 81,831,751 不变，`big_count` −0.8%、`scan_refs` −0.6%、`big_get` +3.3%。flush 分解（200 万行）：段数据 395ms + 索引 34ms + WAL 轮换 22ms（旧路径约 350ms）。**用例教训**：第一版守门用例写错（`flush_bytes=1` 时 WAL 缓冲还没落盘就被丢弃、文件恒 0 字节，两种模式无法区分，**撤修复仍通过**）；改成直接测 `Wal.reset` 语义才有效（撤掉 `setLength` → `expected 0, found 27` 立即失败）。**方法论**：崩塌只有 1/7 概率，跨批次对比会被噪声吃掉；必须「同进程背靠背交替 + 奇偶轮交换先后」+ 专用 A/B 开关，才能把 35% 的差异从噪声里分出来。

- **第八轮审计（2026-11-01，报告 `docs/审计-2026-11-01-第八轮.md`，决策记录七十二；用户原话「先前面的做一次审计，没有问题了再往下推进」）**：审计对象 `c63c75f`。**已修 P1-1**：`Wal.reset()` 的 `written` 清零顺序错了——`setLength` 成功而 `sync` 失败时 `written` 停在旧值，下一次 `flushBuf` 从旧偏移开写 → 文件前段全空洞 → 重开 `parseBatches` 在偏移 0 当撕裂尾 → **之后 WAL 全丢**；改为 `setLength` 成功后立刻 `written=0`，补不变量断言（`sync` 失败路径本身仍无用例，需 mock IO，如实记为缺口）。**已修 P1-2**：WAL A/B 探针（写 570MB）原在 `big_put_strong` 与 `big_get` 之间，违反 §16.1.7「中段重写污染后续指标」→ 移到 `bench_done` 前。**未解决 P1 + 纠正过度结论**：第七十一节「崩塌轮次消失」**不成立**——p10 7 轮干净是运气，追加 p11(3轮1塌)/bare(5轮1塌)/segphase(5轮1-2塌) 后**合计约 1/10 轮次仍变慢**。**教训：故障率 10% 时 7 轮全过概率 0.9⁷≈48%，等于抛硬币；「消失」结论所需轮次必须由故障率反推。** **已用裸写探针定性：不是磁盘慢，是我们自己的写路径**——新增 `bareWriteMbPerSec`（不经引擎，建文件+8MB分块写+每块fsync），在基准起点/`big_put`后/`b8_put`后各打一点；同轮裸写 314–351 MB/s 全程正常，而 `put`（`flush_bytes=1GB` 零段 flush）0.47×、`big_put` 0.72×；同轮 `big_put` 与 `b8_put` 代码/配置/数据量完全相同却差 2–4× → **与执行时刻相关**。**段写三段拆分**（`Writer.ns_create/ns_write/ns_sync`）：fsync 占 235–288ms/394–453ms ≈ **60%**，坏轮 create 4.5×/write 2.5×/sync 2.2× 一起慢。**未验证不得写成结论**：Defender 扫新文件、脏页写回、`std.Io.Threaded` 线程池阻塞。**下一步**：①降 fsync 次数（归档 `archiveAppend` 与 WAL `reset` 的 `setLength+sync` 改组提交，前提是证明「归档落后于段」可自愈）；②探针打「距进程启动秒数」判断固定/随机时刻；③加进程内 write/sync 调用计数。新增观测：`bare_write_mbps`/`bare_write2_mbps`/`bare_write3_mbps`、`big_put_segphase`(create,write)、`big_put_segphase2`(sync,total)。复核通过：`finishBytes` 保证数据段先于归档持久化；`reset` 丢缓冲不丢数据；计时开销可忽略；基准目录无残留且已 gitignore；Debug 跑整套基准 exit=0 无 `bench_failed`；67/67 全绿；`big_disk_bytes` 不变。

- **`flush_bytes` 不是解药 + 写抖动分两类（2026-11-01，决策记录七十三，审计-2026-11-01-第八轮.md §3.6/3.7；用户原话「请继续」）**：为治尾部做 `flush_bytes` 敏感度实验（同进程/同窗口/同 200 万行：8MB→25 次 flush、32MB→7 次、64MB→4 次，7 轮，`zig-2026-11-01-fbsize-run{1..7}.csv`，新助手 `bulkWrite` + `big_put_fb32/fb64` 探针）。**结论：不是解药**——好窗口三者吞吐基本相同（1.9–2.0M，说明 fsync 次数在当前数据量下不是瓶颈）；坏窗口（r6）三者一起崩（406K/544K/534K）；单轮谁快谁慢无稳定规律 → **降 fsync 次数治不了尾部，原计划的「归档/WAL 组提交」不必为这个目的做**。**同时纠正第七十二节「不是磁盘慢」的单一结论**：抖动有**两类**——**A 长窗口（环境级）**：裸写探针 339→**27 MB/s（12×）**、持续数十秒、读全正常（`fbsize` r6：`put` 0.53×、`sql_put` 0.27×、`big_put` 0.21× 但所有读指标正常）；**B 短脉冲（我方更敏感）**：裸写采样正常而引擎写慢 2–4×（`bare` r2、`p11` r2）——我方文件操作/fsync 次数远多于裸写探针（8 次/轮），撞上瞬时停顿概率高。**关键判据：读正常 + 写全崩 + 裸写也崩 ⇒ 存储层写路径问题，不是引擎逻辑**。A 类根因**仍未确定**（写回/NTFS/Defender/SSD 均未验证，不得写成结论），唯一可说的是与「一段时间内写入总量」有关（基准每轮约 1.5GB、六个 200 万行场景）。**下一步需拍板口径**：①基准层（低成本，推荐）轮次间冷却/降单轮写入量、报告区分好坏窗口并**同时给原始值与剔除理由**（只报剔除后=造假）；②引擎层 checkpoint 模型（段 fsync 推迟 + WAL 保留）能再降 fsync 但**治不了 A 类**。
