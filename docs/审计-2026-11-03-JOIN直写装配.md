# 审计报告 · 2026-11-03 · JOIN 直写装配（`5b9e99d`）

**审计对象**：`5b9e99d`（JOIN 反超 SQLite：0.894× → 1.899×）的全部源码改动，
以及它依赖的 `4b1246e`（范围索引 / `DROP INDEX` / JOIN 哈希连接）。

**结论**：发现 **2 个 P1 级所有权缺陷**（都是「出错路径上重复释放 / 泄漏」，正常路径不受影响）、
**1 个 P1 级内存风险**（预分配无上限，大左表会 OOM）、**2 个 P2**（无谓分配、诊断计时口径）。
全部已修，回归 **135/135**、交叉编译 rc=0、性能无回退（`sql_join_index` 988 → 990 µs，噪声内）。

## P1-1 `proj` 的所有权在 4 个调用点各写一套，出错路径**重复释放 `indices`**

**事实**：`buildOutput` 开头有 `defer alloc.free(proj.indices)` —— 也就是说**从它被调用的那一刻起，
`indices` 就归它管**（成功失败都释放）。但 4 个调用点在它**之前**各自写了 errdefer：

| 调用点 | errdefer 释放 | 后果 |
|---|---|---|
| `finishFromValues` | columns + columns 数组 + **indices** | `buildOutput` 内失败 ⇒ indices **释放两次** |
| `finishFromRowsCopy` | columns + columns 数组 + **indices** | 同上 |
| `selectJoin`（`proj_owned`） | columns + columns 数组 + **indices** | 同上 |
| `selectByPk` | columns + columns 数组 | 正确（不碰 indices），但与其余三处不一致 |

**触发条件**：只有 `buildOutput` 内部**分配失败**（OOM）才走到。正常路径不触发，
所以 135 条用例、基准、交叉编译全绿 —— 这属于「只在失败路径上错的缺陷」，
和 §七十二 记过的 `Wal.reset` 顺序问题、§五十 的 `Writer` 泄漏是同一类。

**修法**：引入 `ProjGuard`（`take` / `release` / `deinit`）把所有权说清楚：

- 调用方建好投影即交给守卫，`defer pg.deinit()` 负责**调用 `buildOutput` 之前**的失败路径；
- 交给 `buildOutput` 时用 `pg.release()`，守卫从此不再释放；
- `buildOutput` 补 `errdefer` 释放 `proj.columns`，于是它的语义变成
  **「成功转移 columns，失败自己释放 columns，indices 一直归我」**，四个调用点不再各写一套。

**验证**：`zig build test` 135/135；`selectByPk` / `finishFromValues` / `finishFromRows` /
`selectJoin` 四条路径的用例全绿。
**未覆盖**：OOM 分支本身没有用例（需要注入分配失败），如实记为缺口 —— 与 §五十 同类。

## P1-2 `JoinSink` 预分配按「左表行数 × 投影列数」，**大左表会直接 OOM**

**事实**：`JoinSink.init(alloc, ncols, rowEstimate(left.table))` 里
`cap = expect_rows *| ncols` 然后 `ensureTotalCapacity(cap)`。左表 1000 万行、投影 20 列
⇒ 2 亿个 `Value` = **3.2 GB** 一次性预分配。而 INNER JOIN 的命中数**完全可能远小于左表行数**
（甚至为 0），这笔预分配是纯浪费；更糟的是**分配失败会让本来能跑完的查询报 OOM**。

**修法**：加硬上限 `join_sink_prealloc_cap = 65_536`（`Value` 个数，≈1 MB），
超出的部分交给 `ArrayList` 的倍增扩容。基准档（左表 1 万 × 3 列 = 3 万个）仍在上限内 ⇒ 不触发扩容，
性能无变化。

**验证**：`sql_join_index` 单跑 990.1 µs（改前 988.4 µs，噪声内）。

## P1-3（上一轮遗留，同批修）`reset` 复用游标时**段裁剪跨越区间**

已于 `4b1246e` 修（`initNoPrune`）。列入本报告是因为它是同一条「复用必须重建初始状态」原则的另一处，
且**当前的守卫用例有效**：去掉 `initNoPrune` ⇒ `JOIN` 用例立刻报 `expected 1, found 0`。

## P2-1 排序路径**多分配一次 `wrow`**

`wrow` 是直写路径的宽行暂存，但原来无条件 `alloc.alloc(na + nb)`。改成按需分配时踩到
Zig 的类型推断（`&[_]sql.Value{}` 让 if 表达式变成 `[]const`，`@memcpy` 写不进去）——
最终保留「一条查询一次分配」的写法，并在注释里写明**为什么不再省这一次**：
省它要给两条路径各写一份类型，收益只是一次 malloc。

## P2-2 `assembleMaterialized` 的计时起点传 0

直写路径调用时传 `t0_in = 0`。`timing_enabled` 关闭时无影响（`stamp` 返回 0、整段被 `if` 挡掉），
但一旦有人在 JOIN 上打开计时，`timing.sort` 会累加一个「距进程启动的纳秒数」级别的垃圾值。
改为传 `stamp(io)`。

## 复核通过（无问题的部分）

- **`JoinSink` 的 text/blob 回填**：`flat`/`txt` 都可能扩容，所以只记 `(cell, start, len)` 不记指针 ——
  正确；`materialize()` 里 `toOwnedSlice` 之后 `buf` 已定型，回填出来的切片在 `Rows` 生命周期内有效。
- **左表值不 `dupe`**：`lvals` 在「这一轮」内有效，而 `sink.emit` 在同一轮内就把 text/blob 拷进 `txt`；
  若将来把 emit 改成延迟（批次刷写），必须同时恢复深拷 —— 已在代码注释里写明。
- **`stop_at` 提前终止**：`LIMIT n OFFSET m` 时凑够 `m+n` 停，`assembleMaterialized` 再切 `[m, m+n)`；
  顺序确定（左键升序、同左键时右键升序），结果与「全量再截断」一致 —— 用例覆盖 LIMIT 与 LIMIT+OFFSET 两档。
- **WHERE 在投影之前判**：`sinkJoined` 用宽行 `wrow` 判 WHERE，再挑投影列；
  新增用例覆盖「WHERE 列不在投影里」（`SELECT p.k ... WHERE q.n > 2`）。
- **`MergeIter` 的段裁剪 / `it.corrupt`**：直写路径同样在循环结束后检查 `corrupt`，
  `break :outer`（LIMIT 提前停）之后也走同一句检查 —— 提前停不会把「损坏」当成「读完」。
- **`HashKeyBuf`**：数值键写 9 字节栈缓冲，`text/blob` 才用 `ArrayList`；
  返回切片只在下次调用前有效，`build` 立刻 `dupe`、`probe` 立刻 `get` ⇒ 无悬垂。
- **`JoinHash` 的语义**：数值键统一按 f64 归一（`-0.0` → `+0.0`），命中后再用 `valueCmp` 复核 ⇒
  哈希判等是 `valueCmp` 判等的**充分条件**而不是替代品；NULL 两侧都不入桶。

## 仍存在的缺口（如实记录）

1. **OOM 分支无用例**：`ProjGuard` 修的是「只有分配失败才触发」的重复释放，
   现有手段（`checkAllAllocationFailures`）需要给单个用例挂上，JOIN/装配链路还没做。
2. **`sql_orderby_index10` / `sql_where_orderby_index10` 仍是 0.97× 量级**：
   本轮只确认「无回退」，没解决。差的是「10 次回表 450 ns/次」这条路径，需单独立项。
3. **复合索引 / 后台合并线程化**：两个架构级缺口仍未动（前置条件见 §一百零六结尾）。
