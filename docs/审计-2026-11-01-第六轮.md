## 一、发现的问题

### P1-1 `scanRange` 两遍遍历的越界保护依赖 `std.debug.assert`

`scanRange` 改成两遍遍历后，第二遍假设与第一遍结果完全一致，越界保护写成：

```zig
std.debug.assert(i < n);
const k = buf[off..][0..r.key.len];
```

**`std.debug.assert` 在 ReleaseFast 下会被整个抹掉**（`std.debug.runtime_safety == false`）。
一旦第二遍行数变多（并发写让 memtable 变大、违反「扫描期间不得写」的契约），
`records[i]` 就是**静默的堆越界写**，`buf[off..]` 切片越界也是未定义行为 —— 不是崩溃，是内存破坏。

**影响**：数据损坏级别。虽然单线程契约内不会触发，但「契约被违反时的表现」不该是内存破坏。

**修复**（`table.zig`）：

```zig
while (it.next()) |r| {
    if (i >= n) return error.ConcurrentModification;
    if (off + r.key.len + r.value.len > total) return error.ConcurrentModification;
    ...
}
if (i != n) return error.ConcurrentModification;   // 变少了也要报：否则返回的
                                                    // n 条 records 后半段是未初始化内存
```

### P1-2 懒解析破坏了 `compact` 的「先验证再动磁盘」保证

`compact` 的关键次序有明确注释：

> 关键次序：**先在内存里建好新段**（验证索引可解析），再改磁盘，最后才清理旧段。

但 `Segment.fromBytes` 在懒解析改造后**只读头部、不做 CRC 校验** ——
「验证索引可解析」这一步事实上失效了：一个损坏的索引也会被当成可用，
然后 `archiveRewrite` 让归档指向它。

**修复**（`table.zig`）：建完新段立即 `try new_seg.ensureParsed();`，
把全量校验拉回「动磁盘之前」。同时 `errdefer` 必须注册在 `ensureParsed` **之前**
（否则校验失败时新段的 `entries` 无人释放 —— `fromBytes` 内部的 errdefer 管不到调用方这一层）。

### P2-1 `Replay.deinit` 与 `freeBatches` 是两份相同的释放逻辑

同一段「遍历 batches 逐个 free(ops) 再 deinit」的逻辑写了两遍。改成 `Replay.deinit`
直接复用 `freeBatches`。

### P2-2 懒解析的不变量只有一处断言

`entryKey` 有 `assert(self.parsed)`，但 `mayContain` 与 `candidateIndex` 没有：

- `mayContain` 未解析时 `bits_len == 0` → 返回 `true` → **结果不丢数据，但静默退化成每段全扫**；
- `candidateIndex` 未解析时 `entries` 只有头部带的 1 条 → 二分在 1 条里找 → **结果直接错**。

两者都是私有方法、不返回错误，只能靠断言。已补 `std.debug.assert(self.parsed)`。

## 二、复核通过项（未发现问题）

| 检查项 | 结论 |
|---|---|
| `ensureParsed` 覆盖完整性 | `get` / `scanRefs` / `cursor` / `scanRange` 四个公开入口全部覆盖；`entryKey` / `mayContain` / `candidateIndex` 三个私有访问点均有断言；`firstKey` 只读头部，不需要 |
| mmap 生命周期 | `Table.deinit` 与 `compact` 都是「先 `segs.close()` 再 `idx_map.destroy()`」，顺序正确；`errdefer` 后进先出保证段先关 |
| `compact` 与 mmap 交互 | `archiveRewrite` 的 rename 不会破坏映射（用例 `mmap 存活时 rename 覆盖同路径` 守着），映射在清理旧段后才销毁 |
| `openReplay` 资源管理 | `errdefer` 顺序为 freeBatches → free(buf) → close(f)，无重复释放；成功返回时 `wal` 与 `replay` 各自独立 |
| `ensureParsed` 幂等性 | 失败时 `parsed` 保持 false 可重试；`parseIdxBody` 开头 `clearRetainingCapacity` 保证重试不重复追加 |
| `Table.open` errdefer 顺序 | `segs` 的清理先于 `idx_map.destroy()`（后注册先执行），无悬垂 |

## 三、遗留（记录，本轮不修）

1. **`Segment.open`（单文件模式）仍用 `readWholeFile` 读进堆**，与 `Table.open` 的 mmap 不一致。
   产品路径不走它（只用于测试与单 `.idx` 文件场景），保持现状；
   若将来启用该模式，会重新引入 §16.1.15 的 1.0ms 拷贝。
2. **`mapWholeFile` 把空文件当 `FileNotFound`** → 走「新建库」分支。这与改造前的
   `readWholeFile`（0 字节返回空切片、`archiveCheckMagic` 对空放行）行为一致，
   属于既有边界，不是本轮引入。
3. **`parseIdxHeader` 不校验 CRC** —— 懒解析的固有取舍。头部损坏时 `rows`/`max_seq`
   可能先被用于可见性判定，直到首次 `ensureParsed` 才报 `BadIndexChecksum`。
   数据本身不可信时延迟报错可接受。
4. **`MergeIter.deinit` 依赖 `Table` 仍存活**（要累加 `merge_compares_total`）。
   API 契约：`Table` 必须先于 `MergeIter` 释放。内部使用路径都满足。
5. **`error.ConcurrentModification` 分支无法用现有 API 触发** —— 单线程契约内不可能发生，
   属于防御性检查，与 `maybeAutoCompact` 的 catch 分支同类。
