# 审计覆盖矩阵（一次性审计的判据）

> 这份文档的作用：把「审完了没有」从**口头结论**变成**可核对的表格**。
> 规矩只有一条：**任何一次"审计"在动手之前，先填这张表；表里有空格就不能说审完了。**
> 以前的审计之所以每轮都冒出新问题，就是因为从来没有这张表 —— 见第六节。

## 二、两条已知缺口（都有闸门，不会忘）

| 编号 | 内容 | 闸门 | 关掉的判据 |
|---|---|---|---|
| ~~**K1**~~ | ~~段记录**无校验和**~~ **已关闭（索引 v6）**：写入时增量算整段 CRC32 写进索引头，`Engine.verifyAll()` 显式校验；段注入用例的 `gaps` 棘轮已从 `<= 2` 收紧到 **`== 0`** | `expectEqual(0, gaps)` | 已达成 |
| **K1b** | 归档尾部丢**恰好 1** 个段记录（单次追加崩溃）容忍 | `tolerated <= 1` 棘轮 | 若将来引入"已发布长度"基准，与「归档是权威」的取舍一起重新定 |
| **K2** | §16.5 编译期功能开关：**`-Dsql` / `-Dthreads` / `-Dmmap` / `-Dalloc` 四档全部落地并验证**（D3a/D3b/D3c/D3d） | 四个开关各自 `zig build test -D<开关>=false` 全绿 | **已关闭（2026-11-04）** |

**为什么 K1 不做成「读时验」**（实测数据，不是估）：`crc32Fast` 只有 **1.9–2.1 GB/s**，
一个 1.5 KB 的块要 **775 ns**，而点查总共 **1285 ns** ⇒ 读时逐块验会让点查**慢 60%**。
所以选的是「写入时增量算（写路径 +1~3%，按 2 GB/s 与 24–60 MB/s 写吞吐推算）、
读路径零开销、校验按需调用」。代价要说清楚：**默认查询路径仍然不验 CRC**，
发现位翻转需要显式调用 `Engine.verifyAll()`（或是 `zig build test` 的段注入用例）。

**K1 自身的审计（2026-11-04）抳到 1 处真缺陷**：`verifyAll()` 第一版只遍历基表，
**二级索引表整个被跳过** —— 而索引段损坏的后果比基表更隐蔽（索引项驱动查找，
坏了是**漏行/错行**而不是报错）。已修（`verifyOneTable` + 遍历 `idx_tables`），
并用「翻一位索引段必须报错」的用例钉死。另补两条当时没测的契约：
增量 CRC 任意切分等价（C8）、索引 v5 旧格式可读（C10）。
撤销验证：把 `verifyDataFile` 的比对改成恒真 ⇒ 全量测试全红；恢复 ⇒ 147/147。

**K1/K1b 都是棘轮**：修好只会让计数变小（测试仍绿），**变差立刻红**。这是"已知"而不是"忘了"的机制差别。

```powershell
zig build test -Dthreads=false                                  # D3b：不依赖线程设施
zig build test -Dmmap=false                                     # D3c：不依赖 mmap（堆缓冲后备）
zig build test -Dalloc=false                                    # D3d：固定池模式（源码闸门收紧）
$a='-Dtarget='+'x86_64-linux-musl';   zig build check $a        # D1
$r='-Dtarget='+'riscv32-freestanding'; zig build mcu $r         # D2
zig build check $r -Dsql=false -Dthreads=false                  # C 档组合
zig build -Doptimize=ReleaseFast -Dlite=true; zig-out\bin\spike-bench.exe   # E2
```

红了怎么读：
- `[MISMATCH-*]` / `[MISMATCH-JOIN]` / `[MISMATCH-AGG]` → 语义分歧，后面直接跟着 SQL 与两侧前几行；
- `[life] fail_index=N 记账不平 alloc=.. free=..` → 第 N 个分配点失败时漏释放；
- `[WAL 截断 x/y]` / `[段注入 …]` → 持久化注入，打的是"哪一步、恢复出几行"；
- `Snap` 类棘轮红（`gaps`/`tolerated`）→ 已知缺口变多了，先看是不是新引入的。

## 四、反向自检：这些用例本身是不是摆设？

**每一条注入/差分用例都必须有"防空跑"断言**，否则绿的假测试比没有测试更危险。

| 用例 | 防空跑断言 | 为什么需要 |
|---|---|---|
| 差分 单表/JOIN/聚合/DML | 失败计数 `== 0`，且每条都比**列名 + 每一格值** | 只比行数会漏掉投影顺序错、列错位 |
| OOM 查询 / 生命周期 | 注入点数 `> 20`（实测 18 / 199） | 场景没跑到就等于没测 |
| WAL 截断 | `total > 0` + `max_rows == 行数` + `partial_rows > 0` | 第一版截的是**空 WAL**，全绿但什么都没测 |
| 段注入 | `cases >= 6` + 棘轮 | 段号不存在会被 `continue` 跳过 |

**这条规则是踩出来的**：WAL 用例第一版"通过"时，`Engine.deinit` 会把 WAL 截回 0，
截断的是一个空文件。

## 五、结论口径

- 「审完了」= **上表每一格都有机械检查且全绿**，或该格被显式登记为已知缺口并带棘轮。
- 不允许用「我读了 diff，看着没问题」作为结论 —— 那只覆盖了 19,600 行里的抽样。
- 新增任何能力时，**先在表里加一行**（状态空间 + 检查位置），再动手写代码。

## 六、为什么以前每轮都冒出新问题（留档，防止重演）

| 轮次 | 当时的方法 | 为什么必然漏 |
|---|---|---|
| 1 | 审上一个 diff | 只覆盖"这次改的地方"，且改动的**反面**（失败路径/空结果）没人看 |
| 2 | 审"上一轮的修复" | 修复本身是新代码，从来没被审过 ⇒ 必然还能找到 |
| 3 | 补守卫覆盖（读→写→DDL） | 每补一类就暴露一类，说明**边界是随手划的**，不是枚举出来的 |
| 4 | 三套差分 + 全生命周期 | 开始按**缺陷类别**枚举；扫出 4 处（投影顺序、`open` 键泄漏、`describe` 丢弃、脚手架 UAF） |
| 5 | 补差分缺口（聚合/主键/WAL） | 0 处新缺陷 —— 第一次出现"越审越少" |
| 6 | 持久化注入（段/归档） | 2 处（归档截断已修 + 无校验和已登记），**全部落在 C 类**，没有新类别 |
| 7 | 一次性审计（2026-11-04）：`-Dmmap` + `-Dalloc` + 全矩阵重跑 | **0 处新缺陷**；只修了「守卫自己不可靠」（`checkAllAllocationFailures` 计数会漂）与两处陈旧文档 |

收敛的信号不是"我说没问题了"，而是**新发现的类别数归零**：
第 4 轮起只在已知类别里出问题，第 6 轮没有任何类别外的新发现。

以后再有人说"审一次"，正确动作是：先看这张表有没有空格，再看棘轮有没有红。
